## Storage and identity rules

New composite authority resides in the existing **main-store SQLite file** together with wallet/customer/order/coupon/test state. Existing `users.telegram_id`, not `users.id`, identifies the customer; authenticated tenant is the durable main-store installation UUID, not URL selector or filesystem path. New UUID identifiers are opaque persisted values, independent of local integer IDs and remote names. Web owner principal uses its authenticated web-admin identity with main-tenant/owner role; Telegram owner uses authenticated Telegram identity, explicitly mapped to the configured main owner. A shared number never maps the identity domains implicitly.

Proposed tables below use prefix `composite_` except shared affected ledger/reservation/operation metadata. FKs use RESTRICT for protected dependencies; no cascade deleting financial/history/cleanup. Repeated initialization is versioned/additive and no existing user/service is imported automatically. Existing products/test plans/orders receive default legacy `service_kind` and optional unique composite reference; old records keep their old meaning. Composites are not children in `custom_configs` or stock allocations.

All money is integral shop-wallet units (existing Toman-facing product unit), native money uses exact amount+currency/minor-unit scale and rational/Decimal conversion snapshots; no float settlement. Bytes are nonnegative checked integers within signed 64-bit storage. Duration uses exact positive seconds, absolute times use UTC epoch milliseconds; explicit timezone is presentation only. No calendar rounding. Hashes/fingerprints are non-secret diagnostics; real authentication/subscription tokens/URIs and necessary remote references are encrypted with versioned AES-GCM keys from authorized environment/configuration. Unique random nonces and key IDs are retained; recovery requires keys separately.

## Entities and relationships

### 1. Physical panel, aliases and capability binding

**`composite_physical_panels`**: `physical_panel_id`, installation/authority fingerprint and attestation reference, provider identifier (`3xui` only for composites), endpoint/configuration reference, TLS trust reference, recorded panel/core version, API dialect/capability-manifest revision, route-namespace version, desired deactivation/retirement, confirmed availability/drift, revision. Under RD-10, also: the last verified `restartXrayOnClientDisable` value and check time (must be off, RX-D2; on or unreadable blocks new binding), and write-path stall state with its escalation reference.

**`composite_panel_aliases`**: unique `(database_installation_id, tenant_id, local_panel_server_id)` → physical panel; optional legacy source/mirror reference. Alias mapping requires actual verified physical ownership/authority. URL, identical email, inbound number, `mirror_source_id` or identical local row ID alone never proves identity. Owner registration plus controlled capability validation establishes the mapping; ambiguous aliases hold rather than merge. Addresses may change without overwriting physical server identities during a move.

**`composite_prepared_bindings`**: panel+inbound identity, protocol/transport/security settings fingerprint, ordered intended outbound/egress key, naming/route namespace, versioned readiness/egress evidence and owner activation audit. Shared listener/outbound policy remains owner-managed. Foreign keys retain panel/authorized management references during deactivation/retirement/cleanup. `inbound_id` is qualified by panel. A protected alias/panel cannot be force-deleted.

### 2. Catalog plans, logical nodes and retained offer

**`composite_plans` / `composite_plan_versions`**: catalog identity/version, paid/test/campaign kind, name/category/legacy product or test-plan reference, enabled state, positive finite bytes, duration seconds, base price, method restrictions, owner actor/revision. Paid base price positive and duration exactly 2,592,000 seconds; discounts may produce zero payable. Tests use positive whole-hour durations; quick-check defaults 209,715,200 bytes/3,600 seconds; campaign 16,106,127,360 bytes/1,296,000 seconds. No legacy unlimited sentinel, negative duration, ad hoc grant or customer parameter override.

**`composite_plan_nodes`**: immutable version FK, ordinal, logical node key, prepared binding reference, endpoint descriptor and protocol/security/transport fields (a snapshot read from the panel when the node is saved: address/port from the inbound's External Proxy entry, the rest from the inbound and client; [RD05-OWN-002](research.md#rd05-own-002--export-field-source-and-address-changes-2026-10-22)), the owner's recorded pick where the panel offers several values, owner remark and intended egress. Unique `(version, ordinal)` / `(version, logical_node_key)`; arbitrary positive count, no six/five maximum. Protocol auth choice is VLESS/VMess UUID or Trojan password.

**`composite_offers` / `composite_offer_nodes`**: immutable checkout-accepted copy of price/tier/code eligibility and reductions, base+discounted integral price, byte/duration terms, intended ordered node descriptors/matching signature, method restrictions and revision, acceptance actor/time. These are sold/quoted terms independent of later catalog edits. Renewal matching compares intended protocol/transport/endpoint/egress/node semantics, not plan name/ID alone; authorized equivalent physical bindings retain stable logical signature. The External Proxy address and port are not part of it ([RD05-OWN-002](research.md#rd05-own-002--export-field-source-and-address-changes-2026-10-22) RD05-D8). Separate allowances are permitted for same node signature. Display preset name + stable subscription ID, no personal rename.

### 3. Subscription and independent restrictions

**`composite_subscriptions`**: `subscription_id`, immutable main tenant and `customer_telegram_id`, source initial checkout/test claim, saved offer/node-set identity, paid/test kind, `lifecycle` (`preparing`, `fulfilled`, `cancel_pending`, `cancelled`, `failed_unfulfilled`), initial `available_at`, current paid/test period, common `expires_at`, current config generation and token generation, desired revision, last complete qualified balance/snapshot source time, successful leak replacement time. Cancellation separately records `cancel_accepted_at`, `cancel_wait_kind` (`authorized_renewal`, `initial_provisioning`, or none), waited operation/original deadline, and `cancel_final_started_at`; terminal local cancellation and confirmed remote completion are distinct.

Independent persistent restrictions are `customer_disabled`, `owner_suspended` with owner reason/audit, `reporting_suspended`, `recovery_hold_case` and `replacement_delivery_block`. Cancellation acceptance immediately blocks further renewal funding for this subscription; it is not itself an access restriction during the authorized-renewal wait. `cancel_final_started_at` makes permanent revocation applicable. Separately, cancellation accepted before initial availability sets `initial_delivery_block` immediately (FR-026/PC-095). Derived `expired` and `exhausted` use verified terms/usage/time. Never encode everything into one mutable `enabled` flag. Shop-account block stays in the legacy interaction/account domain. Individual resume clears only its own restriction. Common expiry continues while inactive.

`desired_access` requires verified entitled service/current generation, unexpired and unexhausted terms, no applicable independent access restriction, and no final cancellation started. A fulfilled service in `cancel_pending` with an authorized renewal still uses its existing entitlement and restrictions: pending cancellation alone neither disables access nor invalidates its current URL. Expiry, exhaustion, customer disable, owner/reporting suspension or recovery uncertainty can still restrict it; continued access is not unconditional. Publication separately requires verified ownership/token/complete generation and no initial-delivery, replacement or recovery publication block; owner suspension is status-only, while ordinary expiry/exhaustion/customer/reporting disable retains the complete current list. Final cancellation revokes the token. Do not gate publication on `lifecycle == fulfilled` alone or reject every `cancel_pending` service.

`confirmed_access` aggregates per-child evidence, not a request status: `unknown`, `partial`, `confirmed_eligible`, `confirmed_fresh_auth_denied`. Under RD-10, a `confirmed_*` value requires that no uncertain request for the child that could undo it is still in its quarantine, that a read-back after the latest write matches, and runtime evidence where required. A request carrying the same desired state cannot undo it, nor can an access-reducing request undo `confirmed_fresh_auth_denied` (RX-D8). It is not proof that no late request exists. A later sweep divergence is recorded against it and repaired, never hidden. Native existing-session exposure is separate and never implied stopped by fresh-auth denial.

### 4. URL identity and configuration generation

**`composite_tokens`**: subscription, token generation, unique SHA-256 digest of 256-bit cryptographically random token, encrypted token for authorized customer retrieval, status (`candidate`, `current`, `revoked`, `superseded`), accepted/revoked reason/time. Bearer token grants download only. Retain revoked digests/tombstones; no redirect to replacement token. Leak acceptance invalidates the old token immediately; permanent cancellation invalidates it at final-stage start. Pending authorized-renewal cancellation alone preserves the current token; initial cancellation blocks delivery immediately. Ordinary renewal/move preserves token.

**`composite_config_generations`**: subscription/generation, operation, expected logical nodes, ordered descriptor/content fingerprint, encrypted complete real URI set, capability/provenance references, `prepared_at`, `verified_at`, `retrieval_ready_receipt`, `published_at`, state (`preparing`, `complete_verified`, `published`, `retired`, `blocked_uncertain`). One current complete published generation. Each child can be independently retired even if an unchanged child persists across a move; generation-child membership is explicit. No partial/empty-success publication or automatic native alternate links.

Informational entries are rendered from the existing expiry, qualified usage/source time and public restriction/support snapshot using the [selected VLESS encoding](contracts/subscription-http.md#selected-informational-encoding), supported by GC-MAN-001 owner-reported manual evidence dated 2026-10-10. Their synthetic UUIDs are independent of real generation authentication; they create no `composite_children`, attachment, meter or entitlement records and do not count toward required real-node readiness. They remain available in the permitted owner-suspension information-only response on the same token. G-C is closed using that evidence plus the explicit PR-001 requirement change; information may be selected manually or automatically and fail to connect, with no client skipping/failover/resumption guarantee or automatic-selection validation obligation. This closure does not prove real generation/readiness/gate behavior.

Telegram retrieval receipt records main bot incarnation, subscription+operation+generation+desired revision, handler capability/liveness evidence, customer-visible storage/card readiness and time. Internal URL persistence alone is insufficient. Final availability commit checks complete remote/export state, usable public path, functional authenticated Telegram retrieval and unchanged deadline/cancellation/restrictions. Actual customer click/first use/message reading is not the clock. Bot outage before fulfillment cannot fabricate readiness; bot outage after fulfillment cannot revoke published URLs. Exact liveness demonstration remains E-004 validation, not a paper certificate.

### 5. Child credentials and attachments

**`composite_children`**: stable child identity, subscription/logical node, credential generation, physical panel/canonical remote reference, generated email in prepared route namespace, protocol and encrypted secret, secret fingerprint/subId reference, intended attachment set, meter link, desired state/revision and last confirmed state/provenance; retirement/revocation reason/time, unresolved cleanup reference.

Unique canonical remote identity per physical authority; generated names use opaque collision-resistant identities and route namespace, not customer display name or unchecked Telegram ID. Persist before remote call. Lookup requires canonical reference/email+auth fingerprint+attachments+ownership proof; an unrelated same-name user cannot be adopted. Unexpected missing/renamed/mismatched identity is investigation/hold, not silent recreation. Explicit verified authorized operation can create a new child generation. One fixture node uses one independent credential; the model still distinguishes attachment count from credentials/meters.

**`composite_child_attachments`**: child + server-qualified inbound, protocol settings/flow fingerprint, intended egress binding, expected membership, confirmed membership. Entire API mutation scope must be authorized, even if called for one attachment. Partial results do not create confirmed complete readiness.

**`composite_cleanup_obligations`**: retired/current failed identity, responsible main-store actor/domain, operation/reason, desired fresh-auth denial/removal, confirmed runtime/absence evidence, meter finalization/exposure gap, next observation/retry, escalation/status. Refund/local terminal status never erases it. Native sessions may keep emitting after fresh-auth denial; retain meter/exposure evidence as long as unresolved. Under RD-10, terminal revocation works in three steps:
1. disable at once and record final traffic;
2. delete after the quarantine and either a no-growth settle period P or a maximum wait M from the disable, whichever comes first (RX-D9), batched per panel;
3. record traffic after deletion as unmetered exposure on this obligation, including whether the meter was still growing at deletion. Compaction preserves final totals/epochs/gaps/period allocations and original identifying obligations. No fixed raw-sample retention duration is presumed.

### 6. Meters, observations, deltas and gaps (PR-002; G-A closed)

**`composite_meters`**: stable physical authority+canonical traffic key, owning subscription, scope/capability evidence and standalone-panel authority (no master/node overlay in the supported deployment; PR-002/D10), serving versus retired/emergency-exposure classification, current upload/down epoch and latest accepted observation per direction, last accepted **observation time** (Shopvpn receipt of a valid response, FR-035) and failure state, required-current-serving flag, restart-loss annotations. Unique meter ownership prevents unrelated subscriptions sharing a bucket. Many views/aliases/attachments may reference one meter; one view cannot be charged twice.

**`composite_observations`**: unique local observation ID, meter, per-direction epoch, independent upload/down cumulative values, dispatch time (diagnostic) and receipt time (the observation time; PR-002/FR-035), provenance/restart evidence where a supported read provides it, validity outcome and evidence hash. Acceptance requires HTTP and application success, an object for the verified authority+canonical identity with confirmed ownership/topology and strict nonnegative non-boolean integer upload/download totals. A valid response with unchanged totals is a fresh observation of no new usage; no panel source clock or collector-liveness proof is required. Failed, timed-out, rejected, missing or malformed responses create no observation and never advance observation time; preserve them as diagnostics without replacing accepted time/history. A response received after a newer accepted one for the same meter is diagnostic only: it cannot replace that observation, advance time or generate a consumption increment.

**`composite_meter_deltas`**: unique `(meter, direction, epoch, predecessor observation)`, predecessor/current observation, exact confirmed increment, receipt-time interval, original child generation, billing period, `allocation_state` (`attributed`, `absorbed_exposure`, `gap_affected`). One insertion and aggregate update transaction makes duplicates harmless. Separate up/down epochs permit independent resets. A value at or above its predecessor in the same direction+epoch yields `delta=current-previous`. A lower value opens the next epoch with that observation as baseline, emits no negative delta, preserves all confirmed deltas and records a gap for the bracketing interval; later increments count from the new baseline while pre-decrease loss remains unknown. Each delta belongs to the latest period whose boundary starting reading for that meter direction is at or before its predecessor node; because ingestion and boundary commits serialize on the main-database writer, no delta spans a boundary (`attributed`). `absorbed_exposure` marks only a retired meter's first delta after a boundary at which its latest reading was older than 60 seconds: old-period store-absorbed FR-066 exposure, never renewed-allowance use (PR-002/FR-045, D8).

**`composite_usage_gaps`**: meter/subscription/direction, bracketing observations/times, known lower bound and optional proven upper bound, decrease/reset/missing-history reason, evidence recovery attempts, unresolved versus usage-settled, owner reason/risk actor/time and remaining uncertainty. A settlement absorbs commercial unknown usage but never relabels it measured zero, restores a full allowance or resolves purchase/revocation/financial/campaign history.

Panel/Xray restart baseline loss (PR-002/FR-034; at most four collection intervals, 20 seconds, per restart under owner bound GA-OWN-004 D12) is not a gap: record it as a bounded store-absorbed limitation in the panel capability manifest and as a non-blocking per-meter annotation where a supported read evidences a restart; it is never measured zero, staleness, an FR-040 gap or a renewal block.

**G-A status (PR-002):** Inspected 3x-UI persisted totals supply no panel-side source clock or atomic billing cut, and none is required: approved PR-002 times observations at Shopvpn receipt and attributes usage by reporting order at saved boundary starting readings (§7), so an unsplit interval never needs allocating by commit or HTTP arrival time. `lastOnline`, fixed polling schedules or counter monotonicity remain no substitute for an accepted observation. This model follows [RD-09](research.md#rd-09--renewal-boundary-attribution-from-saved-starting-readings); V-GA-01–V-GA-04 passed on a lab replica of the deployed v3.9.0 standalone panels ([GA-MAN-002](research.md#ga-man-002--v-ga-01v-ga-04-lab-run-2026-10-14)), closing G-A; V-GA-05/V-GA-06 verify the implemented worker before release.

### 7. Entitlement and billing/reminder periods

**`composite_entitlement_periods`**: subscription, unique initial/renewal/conversion operation, grant kind, authorization verification time, old period/expiry snapshot, effective application time, new purchased bytes/duration, eligible carried bytes/time, forfeited seconds, resulting available allowance/common expiry, boundary starting readings, uncertainty qualification, retained offer. Initial test/paid period begins at complete availability.

**`composite_boundary_readings`**: immutable, unique `(period, meter, direction)`: epoch, observation ID, cumulative value and receipt time of that meter direction's latest accepted observation, saved in the same main-database transaction that makes renewal/conversion effective (PR-002/FR-043), after all-child readiness. Every current-serving required meter's reading is at most 60 seconds old at commit, after a worker re-read immediately before commit; otherwise the renewal stays pending inside its original window. Retired meters receive a reading when readable; a stale retired reading is recorded with its age, and that meter's first later delta becomes `absorbed_exposure`. Pending, failed or repeated application creates no additional readings; the commit is keyed by the renewal operation. Initial/test availability and equivalent-move cutover may use the same chain-node rule for new meters (design consequence, RD-09).

Lifetime confirmed usage is never reset. Period allocation separately records `A_old`, old-period usage `U_old` reported through the boundary readings, overrun `O = max(U_old − A_old, 0)` (uncapped), eligible carryover `C`, `A_new`, available `N = A_new + C`, new-period usage `U_new` (later readings minus saved readings across later epochs, never negative), later recovered allocation/corrections and settlement provenance. Old overrun is absorbed; no customer receivable, wallet debit or deduction from new purchased bytes. Usage first reported after the boundary readings consumes `N`, even if part occurred shortly before the boundary within normal reporting delay (PR-002/FR-045). Later recovered evidence for an explicitly recorded pre-boundary gap remains old-period history and never turns beyond-old allowance into new-period debt; no automatic guessed correction. Remaining display floors at zero while actual usage is uncapped.

New renewal funding eligibility: fulfilled noncancelled owned subscription; matching saved nodes; no owner suspension, accepted cancellation, move or dependent recovery/accounting block. Customer disable alone remains eligible. This admission predicate does not terminate an already-authorized renewal when cancellation is pending; that operation resolves under FR-059's original window before final cancellation. At most one open checkout. `timely_payment` records verified/zero-price authorization strictly before prior expiry, never provider claimed paid time/checkout creation. Carry old unspent data only when old term is valid at application or this within-window timely condition holds. New expiry is application time + new 720 hours + old positive remainder capped to 360 hours. Extra old time is forfeited/disclosed. No reuse of failed timely protection. Old access/usage governs pending renewal.

**`composite_reminder_periods` / `composite_reminders`**: one paid logical period per successfully retained initial paid/renewal/conversion, including valid zero-price catalog; resulting new+carried allowance and effective expiry. Each `(period, expiry|quota)` has one logical notice, threshold snapshot, condition+eligibility time, status/attempt/message-service acceptance reference/unknown send. Still-free trial has no optional reminders. Selected quota mode uses percentage (default 80%) or remaining binary data (default 2 GiB), never both/lifetime use. Successful sends do not rearm on toggles/replacement/restart; obsolete notices cancel, eligibility waits retain notice. Exactly-once external send is not assumed.

### 8. Checkout, attempts, receipts and financial obligations

**`composite_checkouts`**: UUID, unique compatibility order FK, immutable tenant/customer/offer, kind (`initial`, `renewal`, `conversion`), target subscription where applicable, acting principal/request idempotency key, status (`quoted`, `awaiting_payment`, `manual_review`, `authorized`, `fulfilling`, `fulfilled`, `rejected`, `cancelled`, `failed`), final store price, actual wallet funding effect/reference, coupon reservation, authorization source/time, original deadline, terminal reason/time, fulfillment operation, original selected funding receipt. Partial unique active target index covers open renewal/conversion through authorized fulfilling; a transaction rechecks eligibility before money or zero-price authorization.

**`composite_payment_attempts`**: checkout, method/provider merchant/config-version namespace, unique local creation intent, provider invoice ID/reference and uncertain-create state, expected native integer/minor amount/currency, expected store remainder, required offset/charges/rate/rounding rules, full original wallet-equivalent invoice value, accepted quote evidence/version/time, validity window/method restrictions, verify recovery identity, status. Quotes are immutable once accepted; new attempt may use current conversion without changing existing attempts/base offer. Unknown remote invoice creation reconciles same intent; no duplicate bill on timeout. A valid safely verifiable issued attempt/manual review counts as a path even when new invoices disabled. No general checkout TTL.

**`composite_payment_receipts`**: unique `(provider, merchant_namespace, transaction_reference)` across main checkout/top-up settlement context, immutable attempt+tenant+beneficiary linkage, verified native amount/currency/full original invoice-value evidence, independent verification/authorized manual actor+reference evidence, `verified_at`, outcome (`original_funding`, `extra_credit`, `terminal_late_credit`, `mismatch_hold`), linked financial effect. Invoice ID is not enough if one invoice can receive distinct real charges; reference must identify each actual receipt. Transaction reuse on another checkout fails/returns original binding. Manual decision and callback are transport events, not money themselves.

**`financial_obligations` / `wallet_effects`** (proposed affected shared tables): unique business effect key, main tenant/beneficiary, kind (`wallet_debit`, `wallet_release`, `full_refund`, `late_credit`, `extra_credit`, `support_compensation`, affected `topup_credit`), immutable amount+unit/evidence, originating checkout/receipt/batch/member, trigger/required-completion time, state (`owed`, `evidence_hold`, `settled`), settled ledger sequence/time. Status and `users.referral_credit` update in the same transaction. Refuse missing beneficiary/unknown prior effect; never clamp an excessive debit to zero or mark queued as settled. Obligations remain independently visible after remote cleanup/credit failures.

Full owed refund = actual original wallet contribution + full original verified invoice wallet value, including quoted required costs. Example 30+73=103; distinct extra receipt 73 is credited independently and not refunded twice. Unfunded cancellation returns wallet once; later verified receipt credits full original value without reopening quote. Positive support compensation is separately authorized and creates no service/campaign/test change. Zero-price authorization creates no paid receipt/refund. Original grant/refund must not wait for discretionary support action.

**`composite_manual_decisions`**: review request/attempt, owner principal+interface, bank/provider reference/evidence digest, checked tenant/customer/amount/unit/method, decision/reason/time/idempotency key. Both Telegram and web call the same settlement transaction. Delegated staff legacy review permissions do not authorize composite decisions. Mismatch remains an owner investigation state.

### 9. Shared reservations and permanent campaign participation

**`resource_reservations`**: unique checkout/claim + resource (`coupon`, `ordinary_test`, `campaign_place`), tenant/customer/code/campaign, accepted monotonic sequence, state (`held`, `consumed`, `release_pending_refund`, `released`, `uncertain_hold`), transition effect key/time. Required shared main legacy coupon/test callers use this guard; neither counter-only decrements nor a composite-only capacity check is safe.

Coupon availability considers permanent consumed uses and all held relevant uses under overall/per-customer restrictions. Successful retained fulfillment consumes; eligible terminal release with required refund waits for its settlement. In-flight-renewal cancellation releases even if success preceded final cancellation; later fulfilled-service no-refund cancellation/support credit does not. Release cannot revive expired/disabled code or grant a future use.

**`composite_test_claims`**: owner/offer, unique pending ordinary request per customer, ordinary reservation and optional campaign place, acceptance sequence/time, unchanged 15-minute deadline, fulfillment/retrieval evidence, terminal delivery-block/cleanup/uncertainty. **`composite_campaigns`**: campaign identity, immutable lifetime cap150, served count/closure and current-history verification. **`composite_campaign_recipients`**: unique `(campaign, authenticated Telegram user)`, unique fulfilled claim, permanent receipt/history. Transaction admission enforces held+fulfilled≤150 and eligible ordering. Uncertain deadline claim retains holds, forbids late delivery and alerts owner; confirmed failure releases once; 150 fulfilled closes permanently. Ordinary reset/max edit, cancellation/expiry/move/conversion never deletes recipients or restores places.

For new operation-based handling, `users.test_used` projects fulfilled ordinary consumption and pending reservations remain separate. The existing `database.py:try_reserve_test_slot:2266` increments that same counter before provisioning, so a pre-upgrade value is not proof that every counted attempt fulfilled. Quiesce affected admissions and reconcile known in-flight attempts during upgrade; preserve every prior count, classify demonstrably pending attempts into retained identity-based holds without counting them twice, and hold any unresolved remainder rather than subtracting it or assuming success. Supported prior-schema fixtures must exercise this ambiguity. Shared eligibility sums preserved legacy consumption and distinct pending holds. Reset only verified ordinary fulfilled counts, not unknown claims; no duplicate release or inherited priority after terminal retry. Permanent campaign history remains separate.

### 10. Lifecycle work, batches, audit and delivery

**`composite_operations`**: unique command/business identity, subscription/checkout/claim/batch, kind, authenticated actor/reason, accepted desired revision, phase/status, original acceptance/authorization/readiness/final-stage clock+deadlines, prerequisite/recovery evidence, worker/restore epoch, last sanitized error/missed-target/escalation. Retry of a pending logical command returns this operation. Permanent cancellation and disable/owner suspension remain admissible while work is busy; conflicting mutation is ordered through current intent, not a generic refusal.

**`composite_remote_work` / `composite_remote_attempts`**: durable operation+child+scope/action/revision idempotency identity, payload fingerprint/encrypted necessary reference, dispatch time, separately retained observed DB/runtime state and prior-request execution evidence, safety mechanism/reference and covered scope, next eligible action, attempts/finite timeout, worker epoch. Status under RD-10:
- `queued` → `dispatched`.
- A timeout or crash makes it `uncertain`, with `quarantine_until` measured from when Shopvpn closed the request's connection.
- At quarantine end a read-back reconciles it to `confirmed` or to a repair write.
- `confirmed` requires no uncertain request for the child that could undo the desired state still in quarantine (RX-D8), a matching read-back after the latest write, and runtime evidence where required. It is not proof that no late request exists.
- An access-reducing desired state is dispatched immediately. After an uncertain access-reducing request, a read-back follows at once and the state is re-sent if not yet applied (RX-D7). A retry of an uncertain create or access-restoring request waits for the quarantine and read-back. An access-restoring change after an uncertain access-reducing request waits for its quarantine (configurable restore wait). Observed absence alone never authorizes replay.
- `manual_hold` retains unresolved work after automatic recovery is exhausted.

*Superseded 2026-10-06 statuses:* `execution_hold`, and `confirmed`/`safe_to_retry` requiring proof that no prior request can still act.

**RX-01 under RD-10 (owner decisions RX-OWN-001, 2026-10-15; amended by [RX-OWN-004](research.md#rx-own-004--rd-10-mechanism-amendments), 2026-10-16):** detect-and-repair replaces the original predicate for composite mutations. It accepts that a late request can temporarily reverse an accepted access state until the continuous sweep repairs it (approved PR-003).

**`composite_drift_sweeps` / `composite_divergences`** (proposed):
- Each sweep run records physical panel and inbound, start/end, outcome (`consistent`, `diverged` or `unknown`) and timeout.
- Each divergence records the child, observed versus desired fields, detection time, repair write reference and outcome, repeat count within window W, a linked FR-041 discrepancy and exposure.
- Divergences are evidence. Compaction never removes them while their exposure or cleanup is unresolved.

Panel stall state lives on the physical panel record. The quarantine applies per child; V-RX-01(c) showed no lost updates between clients of one inbound, so it is not widened to the inbound.

*Original 2026-10-06 predicate, retained as history:* RX-01 requires evidenced completion of the full request and downstream effects, fencing, verified drain, or another validated mechanism preventing late effects from invalidating current required state. Elapsed time, client timeout, lock release, local revision/epoch checks and successful read-back/probes alone are insufficient; a bounded wait qualifies only with an evidenced execution bound or other safety mechanism. No such provider mechanism is established here. The conservative hold covers conflicting mutations across the physical panel and its affected aliases/attachments, including legacy writers; narrow it only with verified mutation-scope/isolation evidence. It does not stop safe observations, other independent panels, local financial settlement or acceptance of protective intent. Publication/completion that relies on held remote effects remains blocked, without making the hold an automatic global access/URL restriction. Keep original deadlines, overdue diagnostics and escalation; an otherwise processable refund never waits for this hold. Obsolete work is superseded only after these execution and current-state conditions hold.

**`composite_batches` / `composite_batch_members`**: owner preview digest, exact subscriptions/customers/action/equivalent mapping, reason/emergency acceptance, authorization/time, per-member operation and result. A changed selection/map needs a new preview. Dedup subscription for service actions; dedup customer for equal positive compensation. No atomic whole-batch rollback: finished members stay finished, retry only unfinished. Authorized move clocks include queues/retries; 150×five benchmark is distinct from campaign cap. Individual completion creates customer refresh notice.

**`composite_audit_events` / `composite_notifications`**: immutable actor domain/action/resource/reason/evidence references, sanitized diagnostics; unique logical notice+recipient (and paid period/type where applicable), current relevance/eligibility and block transitions, immutable original due/target/escalation references and missed-target history, separate opportunity IDs/reasons/event/detection/start/end times, policy version, lifetime automatic network-attempt count/history, dispatch/next-attempt/acceptance/uncertain evidence and explicit recovery audit. States distinguish known-unsent waiting for eligibility/transport/opportunity from actual attempt exhaustion, permanent failure, uncertain delivery, accepted and obsolete. Persist transactional opportunity/attempt claims and never infer unused attempts from incomplete restore history. N-01 window expiry retains unused attempts for automatic relevant catch-up; it neither resets the five-attempt cap nor rearms accepted/uncertain sends. Bind all notification work, including reminders, to N-01 in [operations](contracts/operations.md#notification-delivery-policy-n-01). Private owner reasons excluded from public subscription. Retries preserve logical message identity; prior unknown delivery never claims exactly-once or causes repeat financial/remote effects. Financial/availability outcomes do not wait for message acceptance unless initial retrievability itself is unproven.

### 11. Maintenance, migration and recovery

**`composite_schema_versions`**, **`composite_processing_control`**: supported schema/version/rerun state, installation ID, maintenance admission mode, operation generation, worker incarnation and current restore epoch. An external protected control file stores the installation/restore generation and maintenance state outside replaceable snapshots; all affected processes check it. It is coordination/fencing, not a new financial source of truth. Pre-replacement generation invalidates in-flight acknowledgements/old purge requests; it cannot undo already-sent remote requests, which require reconciliation.

**`composite_recovery_points`**: coherent capture ID/time, schema/release/runtime inventory, manifest members/checksums/FSM dependencies, validation results, separately encrypted archive reference, verified off-host availability/destination identity, last verified capture age/overdue. Persistent delivery attempts record B-01 policy version, immutable capture/hash/destination, unique attempt paths, dispatch/count/next-attempt/budget, partial/uncertain outcome, completion verification and recovery audit; see [operations](contracts/operations.md#backup-delivery-policy-b-01). Do not reset capture age on transfer/validation or treat incomplete set as protected. Database secrets encrypted in recovery artifacts; keys/release/HTTPS/domain/panel prerequisites separately inventoried.

**`composite_recovery_cases` / `composite_recovery_evidence`**: case scope (record/customer/shared campaign/money/panel), old/new epoch, validated point, preserved pre-restore/newer external references, known/unknown facts, restrictions and release/remediation actor/reason. Release independently verified records; shared unknown campaign capacity pauses only dependent claims, widening holds if unsafe shared wallet/history cannot be isolated. Irrecoverable non-usage history requires specific governed remediation; no preapproved risk-acceptance/resume transition. Preserve exact original clocks and retired cleanup through restore.

Destructive guard checks subscriptions, tokens, money/period/campaign/reservations/remote work and all dependent user/order/plan/panel/tenant/key references in the same admission/transaction boundary. Retired inactive panel remains manageable; forced removal/reset does not bypass a guard. Tenant ownership/tier/purge operations that would sever required responsibility refuse or use a separately verified durable custody handoff; launch subscription reassignment stays forbidden.
