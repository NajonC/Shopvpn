## Rules

1. From tasks.md T009, covered here: "a 5-second collector cadence and restart baseline loss" and "per-direction counter decreases: reset, `updateTraffic`, database restore, recreate and periodic reset".
2. Lab and source facts to copy [research.md GA-MAN-002 and the v3.9.0 source check]:
   - "`QueryStats` uses `Reset_: false`; the `StatsLastValues` delta map discards the first pass (`baselinePass`)"; "a statistic lower than its last value is treated as a delta from zero"; "`cadenceXrayTraffic = "@every 5s"`".
   - "Totals never decreased at any restart." "There is no stop-time flush, and a new collector waits about 5 seconds before its discarded baseline pass, so service restarts and panel-only restarts each lost 9.0–13.1 seconds of traffic, while Xray-only restarts lost 1.2–4.6 seconds because the collector's previous values survive."
   - "Reset on the disabled C1 zeroed both directions, only C1 affected, re-enabled C1." "`updateTraffic` supported; download −8 MiB → epoch for download only, upload untouched." "Stop → replace DB → start: C1/C2 lowered by exactly post-backup traffic." "Same-email recreate starts at 0/0." "`hourly` per-client reset … zeroed vga-e in both directions only; inbound totals not reset." "The panel kept counting the disabled client's traffic."
3. **Counters.** Each client present in an inbound has an Xray counter `(up, down)`, starting at `(0, 0)` when it is added or seeded. `serve(email, up=, down=)` adds to it (traffic flowing now, in panel-counted bytes; the fake models no protocol overhead). Disabled clients keep their counter and keep counting. Deleting a client removes its counter and its collector last values; `serve()` for an email without a counter is silently ignored (open sessions after a delete are reported nowhere). `up`/`down` must be `int` and not `bool` (`TypeError`) and `>= 0` (`ValueError`).
4. **Collector.** It has a start time, a `next_tick_ms` and a "baseline pending" flag. At panel creation: start = creation time, `next_tick_ms = start + 5_000`, baseline pending. `collect_due()` runs, in order, every tick with `next_tick_ms <= true_now_ms()`, adding 5 000 ms after each. A tick:
   - baseline pending: set every counter's last value to its current value; change nothing else; clear the flag;
   - otherwise, for each client with a counter and a traffic record, per direction: `cur` = counter; `last` = last value (`None` if absent); `delta = cur` if `last is None or cur < last`, else `cur - last`; add `delta` to the traffic record and to that record's inbound totals (`inboundId`); last value = `cur`.
5. **Catch-up.** `handle()`, `serve()`, `restart()`, `periodic_reset()`, `snapshot()`, `restore()`, `traffic()`, `client()`, `inbound_clients()`, `seed_client()` and `seed_subscription()` first call `collect_due()`. So an event at the same millisecond as a tick happens after that tick.
6. **Restarts.** `restart(mode)`:
   - `"xray"`: set every counter to `(0, 0)`; keep the collector's last values; append `true_now_ms()` to `xray_restarts` and set `xray_started_ms` to it.
   - `"panel"`: Xray keeps running; clear all last values; collector start = now, `next_tick_ms` = now + 5 000, baseline pending. No entry in `xray_restarts`.
   - `"service"`: both of the above.
   - any other mode → `ValueError`.

   Part a's restart on disable/delete (`_maybe_restart`, setting on) is an Xray restart: it now also does the `"xray"` counter reset.
7. **Inbound totals.** An inbound's JSON `up`/`down` is the sum of all deltas added to it (rule 4). Resets, `updateTraffic` and periodic resets don't change it; `restore()` puts back the saved value.
8. **`POST /panel/api/clients/resetTraffic/:email`** becomes a modelled route (node-sync may call it, as today). No client with that email → raise `FakeNotModelled`. Otherwise set the record's `up` and `down` to 0; set `enable` to `True` on the client in every inbound and on its record; set `updated_at`; `obj`: `None`. The Xray counter and last values are untouched, so later traffic counts normally. It never restarts anything.
9. **`POST /panel/api/clients/updateTraffic/:email`** becomes modelled (admin only, as the allowlist already says). In order: no traffic record → raise `FakeNotModelled`; body not a dict → error `invalid traffic body`; `upload` or `download` not an `int`, or a `bool` → error `invalid traffic field: <name>`; a negative value → raise `FakeNotModelled`. An absent key is `0` (Go zero value). Set the record's `up = upload`, `down = download`. `obj`: `None`.
10. **`periodic_reset(email)`**, triggered by the test (fake choice: the fake doesn't schedule resets from the `reset` field): no traffic record → `KeyError(email)`; else set its `up` and `down` to 0, nothing else.
11. **`snapshot()` / `restore(snapshot)`**: a snapshot is a deep copy of the panel database: every inbound's client list and totals, every traffic record, the next traffic id and the settings. Tokens are not part of it. `restore()` replaces those with the snapshot's copies, then does a `"service"` restart (rule 6). After it, every client in the restored inbounds has a counter at `(0, 0)` and no last values.
12. `traffic(email)` returns a deep copy of the traffic record, or `None`.
13. Update the module docstring's basis list for the new behaviour (*lab* or *source* as in rule 2; *fake choice* for rule 3's ignored serves and zero overhead, rule 4's `None` last value, rule 10's manual trigger and the instant restart; the real panel lost 9–13 s per panel/service restart, the fake loses up to 10 s).
