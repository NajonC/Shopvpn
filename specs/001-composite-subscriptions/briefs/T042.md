## Rules

1. "`desired_access` requires verified entitled service/current generation, unexpired and unexhausted terms, no applicable independent access restriction, and no final cancellation started. A fulfilled service in `cancel_pending` with an authorized renewal still uses its existing entitlement and restrictions: pending cancellation alone neither disables access nor invalidates its current URL. Expiry, exhaustion, customer disable, owner/reporting suspension or recovery uncertainty can still restrict it; continued access is not unconditional." [data-model §3]
2. "Publication separately requires verified ownership/token/complete generation and no initial-delivery, replacement or recovery publication block; owner suspension is status-only, while ordinary expiry/exhaustion/customer/reporting disable retains the complete current list. Final cancellation revokes the token. Do not gate publication on `lifecycle == fulfilled` alone or reject every `cancel_pending` service." [data-model §3]
3. Gate order: 1 unknown/invalidated/revoked/superseded token or final cancellation started → opaque 404; 2 unfulfilled, initial delivery blocked, pending leak new delivery, or unverified recovery ownership/current token/generation → 503 ("a still-valid known owner suspension may show safe known status only when ownership/token are verified"); 3 valid verified owner-suspended → 200 information entries only; 4 previously fulfilled token with verified complete current generation, including the authorized-renewal cancellation wait, reporting suspension, expiry, exhaustion or customer disable → 200 complete list; 5 otherwise → 503. [contracts/subscription-http.md "Gate order and response"]
4. "Exhaustion at or above the exact purchased byte threshold or common expiry MUST trigger all-child remote restriction" [spec FR-037]
5. "`confirmed_access` aggregates per-child evidence, not a request status: `unknown`, `partial`, `confirmed_eligible`, `confirmed_fresh_auth_denied`. Under RD-10, a `confirmed_*` value requires that no uncertain request for the child that could undo it is still in its quarantine, that a read-back after the latest write matches, and runtime evidence where required. A request carrying the same desired state cannot undo it, nor can an access-reducing request undo `confirmed_fresh_auth_denied` (RX-D8)." [data-model §3] "Any other uncertain request still blocks confirmation until its quarantine ends, for example an enable while access is being denied." [research.md RX-OWN-004 RX-D8] "Partial results do not create confirmed complete readiness." [data-model §5]
6. "After the latest write" is strict: the schema trigger `composite_remote_work_read_back_after_writes` refuses confirmation when an attempt's `dispatched_at >= observed_at`. A quarantine runs until `quarantine_until`; at that instant it has ended.
7. Enum values are the stored strings: data-model §3 (lifecycle, cancel wait kind, confirmed access), §4 (token status, generation state), §10 (remote work status, sweep outcome) and the `composite_children.desired_state` CHECK.

## Interface T043 builds (also in the test file's docstring)

All in `composite.models`; times are UTC epoch milliseconds.

- `enum.StrEnum` classes, members named as the upper-cased value, in this order: `Lifecycle` (preparing, fulfilled, cancel_pending, cancelled, failed_unfulfilled); `CancelWaitKind` (authorized_renewal, initial_provisioning; "none" is `None`); `ConfirmedAccess` (unknown, partial, confirmed_eligible, confirmed_fresh_auth_denied); `TokenStatus` (candidate, current, revoked, superseded); `GenerationState` (preparing, complete_verified, published, retired, blocked_uncertain); `RemoteWorkStatus` (queued, dispatched, uncertain, confirmed, manual_hold); `SweepOutcome` (consistent, diverged, unknown); `ChildDesiredState` (enabled, disabled, removed); `Publication` (NOT_FOUND, UNAVAILABLE, STATUS_ONLY, COMPLETE_LIST).
- Frozen dataclasses, fields in this order:
  - `SubscriptionAccessFacts(lifecycle, available_at, expires_at, allowance_bytes, used_bytes, customer_disabled, owner_suspended, reporting_suspended, recovery_hold_case, replacement_delivery_block, initial_delivery_block, cancel_accepted_at, cancel_wait_kind, cancel_final_started_at, has_published_generation)`;
  - `AttachmentReadBack(observed_at, matches)`; `UncertainRequest(carries: ChildDesiredState, quarantine_until)`;
  - `ChildAccessEvidence(desired, latest_write_at, read_backs: tuple[AttachmentReadBack | None, ...], runtime_required, runtime_evidence, uncertain_requests: tuple[UncertainRequest, ...])`, one read-back per required attachment, `None` where there is none.
- `is_expired(facts, now)`: `now >= expires_at`. `is_exhausted(facts)`: `used_bytes >= allowance_bytes`.
- `desired_access(facts, now) -> bool`; `publication(facts, token_status) -> Publication` (no time input: expiry never changes what is served); `confirmed_access(evidence, now) -> ConfirmedAccess`: no attachment with a matching read-back after `latest_write_at` → `UNKNOWN`; some but not all → `PARTIAL`; all, with runtime evidence where required and no undoing request with `now < quarantine_until` → `CONFIRMED_ELIGIBLE` for `enabled`, `CONFIRMED_FRESH_AUTH_DENIED` for `disabled` or `removed`. A request undoes the state unless it carries the same state, or both it and the desired state are `disabled`/`removed`.

## Tests (23 functions, 100 cases)

Enums (8 + publication names), fields and frozenness, expiry and exhaustion boundaries, `desired_access` (fulfilled, each restriction alone, the renewal wait with and without each restriction, final cancellation, cancelled, failed initial including a late published generation), `publication` (complete list kept through exhaustion, expiry, customer disable, reporting suspension and the renewal wait; owner suspension status-only, also without a published generation; 404 for revoked/superseded tokens and final cancellation, before owner suspension; 503 for preparing, initial cancellation, pending replacement, recovery hold and no published generation; a failed initial never serves entries), and `confirmed_access` (confirmation, unknown, partial, runtime evidence, RX-D8 harmless and blocking requests with the quarantine boundary, one blocker among harmless requests).

## Left open for T043 (not pinned; the specs don't decide)

1. `desired_access` while `preparing` or during an initial-provisioning cancellation wait. T119 "Prepare children inactive with their exact attachments, then converge access under the current restrictions", so `False` may be wrong there.
2. Whether `replacement_delivery_block` or `initial_delivery_block` restricts access, and whether `desired_access` needs `has_published_generation`.
3. `UNKNOWN` or `PARTIAL` for a child whose attachments all match but which lacks required runtime evidence or has an undoing request in quarantine; the tests only require "not confirmed".
4. `publication` for a `candidate` token; 404 or 503 for `failed_unfulfilled` (the tests accept either); owner suspension combined with a gate-2 condition ("may show safe known status").
5. `is_expired` when `expires_at` is `None`.

Claude's reference (below) answers 1–5 as: `False`; no, yes; `PARTIAL`; 503 for a candidate token or failed initial, 503 for owner suspension with a gate-2 condition; `False`. The T043 brief must settle them, with the owner where needed.
