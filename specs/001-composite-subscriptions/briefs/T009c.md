## Goal

Make the fake panel's writes behave like v3.9.0 under load: writes to one inbound queue behind each other with no timeout; a database hold makes writes wait and then either apply or fail with "database is locked"; a write keeps going on the panel side after its caller gives up, so it can apply later; usage collection stalls during a hold. Later tests use this to check that the composite worker detects and repairs late effects instead of trusting a timeout.

## Rules

1. From tasks.md T009, covered here: "client writes ordered per inbound; … 'database is locked' after about 10.3 s; held requests that apply after the client closes, and requests fully delivered whose response is held".
2. Lab facts to copy [research.md RX-MAN-001, V-RX-01 on v3.9.0 lab replicas]:
   - "10 s database hold: the update applied when the hold ended (+9.1 s). 60 s and 300 s holds: the update failed at 10.3–10.5 s with 'database is locked' and never applied. Inbound-lock queue (four writes queued behind a slow update on the same inbound): applied +62.2 s after dispatch, about 51 s after the client gave up. Reads kept working during every hold. Usage was not reported during a hold … for every meter on the panel."
   - "Three queued writes committed in send order within 17 ms when the hold ended. C1 ended disabled and C2 enabled, as intended."
   - "d-before: 'record not found'. d-afterA and d-afterB: the client ended absent with no window of access. d-c4: a create that timed out landed 15 s after dispatch, after a read-back had returned 'not found'."
   - "slowbody: the held update survived the restart and applied after it. Panel API down about 14 s."
   - "b2-late (whole request delivered, response held) executed 3.5 s after the client closed."
   - Source: "`lockInbound`: client updates wait on a per-inbound lock with no timeout"; "`Update` looks the client up before changing it"; "writes to one inbound therefore reach the database and running Xray in the same order".
3. **Writes and reads.** Writes are the five routes `clients/add`, `clients/update/:email`, `clients/del/:email`, `clients/resetTraffic/:email`, `clients/updateTraffic/:email`. Everything else is a read. Reads are answered at once and never wait for a hold or a stall (only for held responses, rule 8). The 404/401/403 answers and `FakeNotModelled` for unmodelled routes also happen at once.
4. **Dispatch.** A write that passes authentication becomes a pending write with a dispatch sequence number. Its inbound set is fixed at dispatch from the current state, before any lock, as the real `Update` reads first: `add` → the listed `inboundIds` that are integers and exist; `update`, `del` and `resetTraffic` → the inbounds the client is in now; `updateTraffic` → the traffic record's `inboundId`; nothing found → the empty set. `pending_writes` counts writes dispatched and not yet finished.
5. **Per-inbound queue.** A pending write may start when none of its inbounds is stalled, none is held by a started write, and no earlier, not yet started write shares an inbound with it. A write with an empty inbound set starts at once. A started write holds its inbounds until it finishes. Whenever a write finishes, a stall is released or the database is released, start every write that may now start, in dispatch order. There is no timeout on this queue.
6. **Database.** When a write starts and the database is not held, it executes at once: the existing handler logic runs against the current state (the client may have been deleted meanwhile; then it fails as the handlers already say, for example `record not found`, and never recreates anything). When the database is held, the write waits from that moment. If `release_database()` comes before `wait start + DB_LOCKED_AFTER_MS`, it executes at release; at `wait start + DB_LOCKED_AFTER_MS` it fails instead with error `database is locked` (`{"success": False, "msg": "Request failed (database is locked)", "obj": None}`) and never applies. Either way it then finishes.
7. **Collector during a hold.** A baseline tick changes nothing in the database, so it runs as before. A normal tick computes its deltas and updates the last values as before; if the database is held, it waits like a write: its deltas are added at release if that comes before `tick time + DB_LOCKED_AFTER_MS`, otherwise they are lost at that time. All waiters (writes and collector ticks) execute at release in the order they started waiting.
8. **Held responses.** While `hold_responses()` is on, every answer `handle()` would return (reads, writes, 404/401/403) is kept back; writes still execute as rules 5–6 say. `release_responses()` delivers the kept answers in the order they were produced.
9. **Giving up.** `handle()` awaits its answer through `asyncio.shield`, so cancelling the caller never cancels the pending write: it stays queued and applies later. The answer is then dropped. When nothing waits or is held, `handle()` must finish without awaiting anything, so part a and b's synchronous `asyncio.run(...)` calls keep working.
10. **Errors in a deferred write.** If a write that executes later raises `FakeNotModelled` and its caller is still waiting, the caller gets the exception. If the caller gave up, the call that made it execute (`release_database()`, `release_inbound()` or `run_due()`) raises it after finishing all its other processing.
11. **Time.** `run_due()` processes, in time order, every collector tick and every lock deadline due by `true_now_ms()`; at the same millisecond, deadlines go before ticks. `collect_due()` becomes the same function. Every public method still calls it first, and `release_database()` / `release_inbound()` call it before releasing.
12. **API down.** `api_down()` makes `handle()` raise `ConnectionRefusedError` before doing anything (no call recorded, no catch-up); `api_up()` ends it. Pending writes survive, also across `restart()`.
13. **Restarts and restore.** `restart("panel")` and `restart("service")` drop collector ticks waiting on the database (their deltas are lost) but keep pending client writes. `restore()` raises `FakeNotModelled` while any client write is pending.
14. **Misuse.** `hold_database()` while held, `release_database()` while not held, `stall_inbound(i)` while that inbound is stalled, `release_inbound(i)` while it isn't, `hold_responses()` while held and `release_responses()` while not held each raise `RuntimeError`. An inbound id the panel doesn't have raises `KeyError` in `stall_inbound` and `release_inbound`.
15. Seeding helpers (`seed_client`, `seed_subscription`) and `serve` ignore holds and stalls.
16. Add this part to the module docstring's basis list: *lab* for rules 5–9 and 12; *source* for the queue's missing timeout and the lookup before the lock; *fake choice* for the exact 10 300 ms threshold (the lab saw 10.3–10.5 s), the collector loss model (the lab lost about 39 s of usage per 60 s hold; the fake loses every tick older than the threshold) and the instant API outage.
