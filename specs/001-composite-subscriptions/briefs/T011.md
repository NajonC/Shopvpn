## Goal

Give later tests two tools. `crash.py` provides named crash points: a `CrashPlan` that production code will receive as an optional hook and call immediately before and after each commit, remote dispatch and remote result. `multiprocess.py` runs a function in several spawned processes at once, each with its own SQLite connections on synthetic files in a lab folder, each guarded like the test process. A child whose armed crash point is reached dies on the spot, so only what SQLite committed survives; a "restart" is simply another run on the same files and clock.

Under pytest, `_state.lab_roots` holds pytest's base temp folder. Children are not guarded today ("Child processes started by a test are not guarded").

## Rules

1. Task [tasks.md T011]: "It runs separate processes and connections on synthetic files, with named crash points before and after each commit, each remote dispatch and each remote result". [plan.md "Validation and traceability"]: "real multi-process integration for transactional uniqueness/crash ordering/locks/capture/restart. Inject crashes immediately before/after each DB commit and remote dispatch/result". [quickstart.md]: "Restart with same state and clocks"; "Multi-process tests use separate connections/processes on synthetic files to exercise SQLite locks; no in-memory-only substitute for actual concurrency."
2. Owner decision (2026-10-26): production code receives the crash hook as an optional parameter that does nothing by default; it is never switched on by configuration or environment. Nothing is added to `composite/`. Say this in `crash.py`'s docstring.
3. **CrashPlan.** `arm(point, *, hit=1)` arms a point to crash on the `hit`-th time it is reached after arming, and returns the plan. Calling the plan with a point name records it in `reached` (in order), then, if that point is armed and this is its `hit`-th reach, disarms it, sets `crashed_at` and crashes. A point crashes once; several points may be armed; `crashed_at` is the latest crash. Names must be non-empty `str` (`TypeError` for other types, `ValueError` for `""`), in `arm` and in calls; `hit` must be an `int` that isn't a `bool` (`TypeError`) and `>= 1` (`ValueError`). Invalid calls record nothing. A plan pickles to an independent copy.
4. **How a crash happens.** In the test process: raise `SimulatedCrash(point)` (a `BaseException`, not an `Exception`, with attribute `point`). Inside a harness child: first report the point as reached and as crashed to the parent, then call `os._exit(CRASH_EXIT_CODE)` at once (no `finally`, no flush, no cleanup), so SQLite keeps only committed work. `CRASH_EXIT_CODE = 86`. `crash.py` knows it is in a child because the child bootstrap installs a module-level reporter there; only the harness sets it.
5. **run_processes**, in order:
   1. Validate: `count` an `int >= 1`; `plans` `None` or a sequence of length `count` whose items are `CrashPlan` or `None`; `lab_root` an existing directory whose real path is inside one of the current `network_guard._state.lab_roots` (none, or outside → `ValueError`).
   2. Start `count` children with `multiprocessing.get_context("spawn")`. Use only `Pipe(duplex=False)` (one per child, for reports) and one `Barrier(count)`. Don't use `Queue` (its feeder thread loses messages at `os._exit`), `Manager` or `Listener` (they open Unix sockets outside the lab root, which the guard refuses).
   3. Each child: `network_guard._state.install()`, then sets `lab_roots` to exactly `{realpath(lab_root)}`; installs the crash reporter; builds `ChildContext(index, count, Path(realpath(lab_root)), plan or CrashPlan(), clock)`, where `plan` and `clock` are the pickled copies passed in; waits on the barrier (timeout `timeout_s`), so all children start the target together; calls `target(context, *args)`; reports the return value and `context.clock`. If the target (or the barrier) raises, it reports the exception's type name and its formatted traceback text and exits with code 1.
   4. The parent reads every pipe while it waits, so a child never blocks on a full pipe. If any child is still alive `timeout_s` real seconds after the start, it kills every live child, joins them and raises `TimeoutError`.
   5. It returns one `ChildResult` per child, in index order. `value` and `clock` are set only when the target returned; `crashed_at` only for a crash; `error_type`/`error` only for an exception; `reached` lists the points the child reported. If any child reported a `NetworkGuardError`, raise `NetworkGuardError` in the parent with that child's message (after all children have finished); don't call the guard's record or deny functions.
6. `run_processes_async` takes the same arguments and runs `run_processes` in a worker thread (`asyncio.to_thread`), so the test's event loop keeps running (for example an HTTPS fake panel the children call).
7. Targets, arguments, plans, clocks and return values must be picklable; targets must be module-level functions. The parent may poll with short real sleeps; children use real processes and real SQLite locks. Nothing logs.
8. Docstrings say: in the test process a crash is an exception, so `finally` blocks and context managers still run; only a harness child crashes for real. Children are guarded like the test process.
