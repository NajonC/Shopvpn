## Goal

Add two controlled test substitutes, both labelled "substitute, not evidence". A fake payment method adapter quotes, creates invoices and verifies receipts against an in-memory provider that tests steer: exact, short or foreign-currency payments, missing or unparseable amounts, refusals, outages and lost create responses. A fake Telegram bot stands in for aiogram's `Bot.send_message`, with lost responses, retry-after, blocked chats and crashes after dispatch. Later finance and notification tests drive the real service code against them.

- `tests/_harness/fake_threexui.py`: an earlier substitute; copy its style (module docstring with "substitute, not evidence" and a basis list, `EVIDENCE_LABEL`, frozen dataclasses, a token-free `__repr__`).

Build errors as `TelegramRetryAfter(method=…, message=…, retry_after=n)` and `TelegramForbiddenError` / `TelegramBadRequest` / `TelegramNetworkError(method=…, message=…)`, with `method=aiogram.methods.SendMessage(chat_id=chat_id, text=text)`. Build replies as `aiogram.types.Message(message_id=…, date=…, chat=aiogram.types.Chat(id=chat_id, type="private"), text=text)`. Never create an aiogram `Bot` or session.

## Rules

1. Task [tasks.md T010]: "`tests/_harness/fake_payments.py`: a method adapter that can return confirmed, rejected, uncertain, a repeated hint, a mismatched amount or currency, and a missing or unparseable amount; `tests/_harness/fake_telegram.py`: acceptance with a message reference, a lost response, retry-after, permanent rejection and a crash after dispatch".
2. Adapter contract [contracts/application.md]: "`quote_attempt(checkout, method_config_version, requested_remainder) -> AttemptQuote`; `create_or_reconcile_invoice(persisted_attempt_intent) -> InvoiceObservation`; `verify_receipt(persisted_attempt, notification_hint) -> VerifiedReceipt | EvidenceFailure`". "Repeated hints are not distinct receipts. No missing/unparseable/malformed/nonfinite amount … settlement." "`EvidenceFailure`: definite rejection versus uncertain/unavailable, sanitized missing field/reason and safe requery/reference. Generic unverified webhook success cannot settle." The owner decided (2026-10-26) that until T075 builds the real types in `composite/finance.py`, this module defines them; say so in its docstring.
3. Telegram [contracts/operations.md N-01]: "Verified Telegram acceptance/message reference is terminal `accepted`… Lost response, ambiguous service error or crash after dispatch is `uncertain_delivery`"; "a larger service retry-after sets a later `next_attempt_at`"; "Permanent recipient/auth/payload rejection stops automatic sending immediately".
4. **Quote.** `requested_remainder` that is not an `int` (a `bool` counts as not an int) → `TypeError`; `<= 0` → `ValueError`. `invoice_value_units = remainder + charge_units`; `native_amount` = the smallest multiple of `rounding_increment` that is `>= invoice_value_units * rate_minor_per_unit` (integer arithmetic only); `rounding_mode = "up"`; `valid_until_ms = clock.now_ms() + validity_ms`; `evidence_version = method_config_version`; `checkout_id` from the checkout.
5. **Invoice creation**, in this order: provider unavailable → `InvoiceObservation(intent_key, "uncertain", None, "provider unavailable")`, nothing created. The intent already has an invoice → `(intent_key, "created", that id, "")`. `reject_next_create()` armed → disarm, `(intent_key, "rejected", None, "create rejected")`, nothing created. Otherwise create invoice `inv-1`, `inv-2`, … (numbered per method object), remembering the attempt (linkage and quote); then if `lose_next_create_response()` is armed → disarm and return `(intent_key, "uncertain", None, "response lost")` (the invoice exists, and the next call with that intent returns it as `"created"`), else `(intent_key, "created", id, "")`.
6. **Verification**, in this order:
   1. Provider unavailable → `EvidenceFailure(False, "provider unavailable", None, None)`.
   2. No invoice for `attempt.intent_key` → `EvidenceFailure(True, "no invoice for this attempt", None, None)`.
   3. A hint that is a dict whose `"transaction"` is a `str` names a transaction: unknown → `EvidenceFailure(True, "unknown transaction", None, None)`; on another invoice → `EvidenceFailure(True, "transaction belongs to another attempt", None, None)`. Every other hint content (`"status"`, `"amount"`, …) is ignored; a hint without a string `"transaction"`, or `None`, counts as no hint.
   4. No hint: a refused invoice → `EvidenceFailure(True, "payment refused", None, invoice_id)`; no transaction yet → `EvidenceFailure(False, "no payment found", None, invoice_id)`; otherwise the invoice's first transaction.
   5. Raw amount `None` or `""` → `EvidenceFailure(False, "amount missing", "amount", transaction_id)`; any other value that is not a `str` fully matching `[0-9]+` (ASCII digits only; so not `"NaN"`, `"1e6"`, `"-1"`, `" 1"`, `"1.0"`, Persian digits or an `int`) → `EvidenceFailure(False, "amount unparseable", "amount", transaction_id)`.
   6. Raw currency `None` or `""` → `EvidenceFailure(False, "currency missing", "currency", transaction_id)`.
   7. Otherwise `VerifiedReceipt` with the invoice's attempt linkage and quote, `native_amount=int(raw amount)`, the raw currency, `verification_source="fake provider API"`, `verified_at_ms=clock.now_ms()`. An amount or currency that differs from the quote is reported as paid; the service decides to hold it. The same transaction always gives the same `transaction_reference`.
7. **Provider controls.** `pay(invoice_id, *, amount=<exact>, currency=<exact>) -> str` adds transaction `txn-1`, `txn-2`, … (numbered per method object); the defaults are `str(quote.native_amount)` and the quote's currency; any value passed (including `None`, `""`, an `int`) is stored as given. Unknown invoice → `KeyError`; refused invoice → `ValueError`. `refuse(invoice_id)`: unknown → `KeyError`; an invoice with a transaction → `ValueError`. `hint_for(transaction_id)` → `{"invoice_id": …, "transaction": …, "status": "paid", "amount": <raw amount as stored>}`; unknown → `KeyError`. `set_available(bool)`, `lose_next_create_response()`, `reject_next_create()`.
8. **Calls and secrets.** `calls` is a tuple of adapter method names (`"quote_attempt"`, `"create_or_reconcile_invoice"`, `"verify_receipt"`), appended when each call starts; controls are not recorded. `api_key` is `secrets.token_urlsafe(32)`, new per object, and never appears in any `repr`, `str`, result or reason; `repr(method)` shows only the method and merchant names.
9. **Telegram send**, checks in this order, each call appending `FakeSendAttempt(chat_id, outcome, clock.true_now_ms())`:
   1. `text == ""` → `TelegramBadRequest` with message `"Bad Request: message text is empty"`, outcome `"rejected"`.
   2. Blocked chat → `TelegramForbiddenError` with message `"Forbidden: bot was blocked by the user"`, outcome `"rejected"`.
   3. Retry-after window open (true time before its end) → `TelegramRetryAfter` with `retry_after` = remaining milliseconds divided by 1000, rounded up, message `f"Too Many Requests: retry after {n}"`, outcome `"retry after"`. The window applies to every chat.
   4. The oldest queued outcome, if any, is taken: retry-after `n` → opens the window for `n * 1000` ms from now and raises `TelegramRetryAfter(retry_after=n)`, nothing delivered, outcome `"retry after"`; lost response → deliver, then raise `TelegramNetworkError` with message `"Request timeout error"`, outcome `"lost response"`; crash → deliver, then raise `CrashAfterDispatch`, outcome `"crashed"`.
   5. Otherwise deliver and return the `Message`, outcome `"accepted"`.
   Refusals in steps 1–3 leave the queue untouched. Deliver: `message_id` counts 1, 2, … per chat; append `FakeSentMessage(message_id, chat_id, text, clock.true_now_ms())`; the `Message.date` is `datetime.fromtimestamp(true_ms // 1000, tz=timezone.utc)`. Extra keyword arguments (`parse_mode`, `reply_markup`, …) are accepted and ignored.
10. **Telegram controls.** `queue_lost_response()`, `queue_crash_after_dispatch()`, `queue_retry_after(seconds)` (not an `int` or a `bool` → `TypeError`; `<= 0` → `ValueError`), `block_chat(chat_id)`, `unblock_chat(chat_id)`. `CrashAfterDispatch` subclasses `BaseException`, not `Exception`, so ordinary `except Exception` cannot swallow it. Message text is kept out of every `repr` (it can hold a subscription URL).
11. No network, no real time, no sleeps, no logging. Each module docstring contains "substitute, not evidence" and lists the basis: *contract* for the result fields and outcomes (rules 2–3); *source* for the aiogram error classes and the two Telegram error texts; *fake choice* for everything else (numbering, the quote formula, ASCII-digit amounts, global retry-after window, per-chat message ids).
