## Selected technical decisions

### RD-01 — Add a main-store composite domain alongside legacy services

**Decision:** Proposed `composite/` package and explicit `service_kind` discriminators in affected products/test plans/orders. Separate composite entitlement, generation, child, meter, checkout and operation tables in the existing main SQLite database. Keep legacy `custom_configs`/stock records intact; no fake panel or synthetic legacy service per child. Orders provide a guarded receipt/catalog compatibility projection, not composite authority.

**Rationale/evidence:** Main-store-only sales avoid cross-tenant financial settlement; existing user ownership commonly uses Telegram IDs. New identities cannot fit single-panel legacy renewal/delete/alert assumptions. Reuse factory, price/method settings, owner authentication, wallet display and test entry behavior.

**Alternatives:** Extending `custom_configs` to mean both parent and child or making one dummy-panel parent hides incompatible semantics; a separate database would split wallet/entitlement atomicity. **Trade-off:** Explicit dispatch/selector guards at all affected entry points and shared wallet/coupon/test primitives are required. Main buyers with reseller status remain ordinary buyers. No composite purchase referral/commission hook or first-purchase flag consumption. No legacy import, reassignment or off-catalog grant.

### RD-02 — One local transaction per commercial transition; durable outbox

**Decision:** Short explicit `BEGIN IMMEDIATE` transactions on dedicated connection ownership; immutable receipt/effect keys, conditional balances, partial uniqueness for one open renewal, and transactionally recorded remote/notification work. Network waits stay outside transactions. Main-store checkout, wallet, coupon/test reservations and entitlement live in one file. Related wallet approval/refund updates use the same transaction primitive, not nested committing `Database` helpers.

**Evidence:** SQLite has one writer, and WAL does not provide crash-atomic commits across attached databases. [Transactions](https://www.sqlite.org/lang_transaction.html), [ATTACH](https://www.sqlite.org/lang_attach.html). Python's legacy `executescript` may commit pending transactions; migration code must own transactions explicitly. [Python sqlite3](https://docs.python.org/3.11/library/sqlite3.html).

**Trade-offs:** WAL remains local-filesystem only; no ORM, Redis, broker, PostgreSQL or distributed transaction coordinator. Select `synchronous=FULL` for all writers of affected main financial state, including reused `Database` connections, and verify pragma values. Isolate DB work in bounded thread executors. Short 1-second feature busy waits with bounded retries must surface overload; existing four-second legacy waits need characterization. Do not retry an indeterminate commit blindly: reopen and query the unique effect. [WAL](https://www.sqlite.org/wal.html), [synchronous](https://www.sqlite.org/pragma.html#pragma_synchronous).

Cross-DB legacy supplier/tenant effects remain outside composite selling; dependent changes use a main-owned transfer/recovery record with tenant idempotency marker, never an atomicity claim. Both sides join recovery capture/holds. The most conservative remedy for destructive composite dependencies is refusal, not a new customer-transfer feature.

### RD-03 — Persist intent, serialize remote writes, reconcile ambiguity

**Decision:** Persist all intended secrets/attachments/meter ownership and operation identities first. Use provider optional capabilities for explicit disabled preparation, canonical reads, absolute field application, strict metering, export and revocation. One authoritative composite worker obtains an OS process lock; all affected Shopvpn writes on a physical panel use a provider-level OS file lock and durable unresolved-scope marker. Legacy affected 3x-UI callers join that coordinator; external owner edits remain detectable drift.

**Rationale:** Upstream may mutate a canonical email or trigger shared changes. Conservative per-panel mutation serialization avoids new local overlaps but cannot stop a previously dispatched request. Restriction acceptance is a local transaction and never waits for a long network lock. Originally, no conflicting mutation or retry was allowed while prior remote execution was unresolved. Under [RD-10](#rd-10--rx-01-detect-and-repair-with-continuous-reconciliation), a changed access-reducing state is dispatched immediately, while retries of the same state and access-restoring changes wait for the uncertain request's quarantine. Stop/restart invalidates old local acknowledgements; reacquisition needs execution-safety evidence as well as current remote ownership/state before issuing another mutation.

**Alternatives/trade-offs:** A DB lease alone cannot fence an already-sent remote request; no assumed provider idempotency key or remote revision check. Serialize instead of parallel mutating the same panel. Different panels and bounded reads can progress concurrently. An ambiguous request can delay dependent work and requires visible owner recovery; durable holds must not silently deny protective requests or reset their clocks. Native runtime fresh-authentication proof is capability-gated, never `success:true` alone. Do not invoke bulk/reset/restart shortcuts that disturb unrelated users.

**RX-01 — prior-execution safety (extension of the existing E-001/E-002 provider capability gate); direction revised by owner decisions RX-OWN-001 in [RD-10](#rd-10--rx-01-detect-and-repair-with-continuous-reconciliation), 2026-10-15:**
- Inspected 3x-UI v3.9.0 offers no request fence or revision check, and its per-inbound client lock has no timeout, so the original predicate below has no available mechanism.
- For composite mutations it is replaced by detect-and-repair:
  - absolute writes;
  - changed access-reducing states dispatched immediately;
  - an uncertain request's quarantine and reconciling read-back before a retry, an access-restoring change or a "confirmed" claim;
  - a continuous per-inbound sweep that repairs and records late reversals;
  - escalation of repeated divergence and panel stalls.
- The owner accepts that a late request can reverse an accepted access state until the next sweep repair.
- RX-01 stays open until V-RX-01 passes. The original 2026-10-06 predicate is retained below as history.

*Original predicate:* Observed desired state and evidence that a previous request cannot change it are distinct. Before clearing the physical-panel conflicting-mutation barrier, require evidenced full completion including downstream effects, fencing, verified drain, or another supported mechanism excluding late invalidation, plus current ownership/state/intent checks. Narrow the hold only with proven scope/isolation; include aliases/attachments and affected legacy writers. Timeout, elapsed time, local lock release/revision/epoch checks or successful reads/probes do not establish this. A bounded wait works only with an evidenced execution bound or other safety mechanism. Keep unresolved holds, diagnostics, missed deadlines and escalation while continuing safe reads, other independent panels, accepted protective intents and otherwise processable local refunds. Correcting this contract does not supply a provider mechanism: none is established, and dependent remote implementation remains blocked.

**Source-based failure scenario, not a reproduced runtime result:** Local `panel_providers/threexui_provider.py::_post_client_update` posts client fields and converts client/network timeout into `PanelError`; it provides no server execution-completion evidence. The pinned upstream `ClientService.Update` prepares per-inbound applications, runs fanout and then performs further record writes including `enable`; the inspected method takes no caller revision/fence or request cancellation context. A delayed earlier enable can therefore be considered in validation even after reads/authentication probes see the currently required disabled state. This is an inference requiring controlled V-RX-01, not proof of deployed scheduling or cancellation behavior. Under RD-10 the owner accepts this residual instead of requiring prevention. The expanded V-RX-01(i)/(k) cases check detection and repair of exactly this ordering. See [pinned update implementation](https://github.com/MHSanaei/3x-ui/blob/815c9c57726d0c5df77878da3f49a5d6b95c6c46/internal/web/service/client_crud.go) and [provider RX-01 contract](contracts/provider.md#remote-execution-and-fencing). No gate passes from source inspection alone.

Cancellation uses FR-058–FR-060/PC-073–PC-075 phases: pending acceptance blocks further renewal funding while existing entitlement/expiry/quota/independent restrictions govern access and publication; pending intent alone does not revoke or invalidate during authorized-renewal wait. ### RD-08 — Consistent recovery set, guarded restoration

**Decision:** Add affected-schema versioning and repeat-safe additive migrations; common maintenance admission gate and OS locks for every writer, FSM, reconciler, purge and API/bot/worker. For backups, stop new related mutations, drain in-flight work, freeze a coherent capture set, use SQLite online backup, validate schema/integrity/invariants and manifest/checksums, include dependent tenant databases/FSM, encrypt and deliver off-host with verified host identity. Target capture every five minutes with validated delivery within the rolling fifteen-minute age objective; E-004 must establish margin, never file-time freshness.

Delivery binds to [B-01](contracts/operations.md#backup-delivery-policy-b-01): 10-second connect, 30-second no-progress and 120-second full-attempt limits; three attempts with 15/45-second backoff, bounded by capture+600 seconds and any earlier still-current last-valid-capture+900-second limit. A new capture after protection is already overdue may attempt bounded recovery under B-01 while preserving the original miss. Persist partial/uncertain uploads, verify immutable attempt-specific archive/manifest integrity, preserve the valid predecessor and retain original capture age on every retry/later recovery. Full read-back bandwidth and temporary storage need E-004 sizing; no extra paid capacity or new routine owner duty is assumed. The candidate five-minute cadence and fifteen-minute recovery-point objective remain unmeasured and unchanged.

**Evidence/alternatives:** SQLite online backup gives a consistent individual snapshot, not a simultaneous multi-file cut. [Backup API](https://www.sqlite.org/backup.html). Uncoordinated file copying or sequential live captures are rejected. Brief global affected-writer pause is simpler than adding a cross-file journal service; timing impact must be measured. Do not stop remote VPN sessions for backup.

Restore validates the entire staged archive before replacement, detects missing/corrupt members and both reseller filename conventions, retains a complete pre-restore set and installation UUID/restore generation outside replaced files. Stop and verify all writers closed; reconcile newer accessible local/external evidence before dependent financial/access/campaign/destructive mutations. Snapshots alone cannot reconstruct lost money or revocations. Release verified cases individually; missing irrecoverable non-usage history requires specific governed remediation, not a generic resume button. Outdated commands/purges cannot run against a new restore epoch.

Prior binaries cannot safely read composite semantics after issuance; rollback uses the same feature-aware compatible release or full coordinated restoration with reconciliation, not dropping tables or reverting to old code over active children. Required configuration/decryption keys, domain/TLS and prepared panel state are external recovery prerequisites; never store keys with their encrypted archive. No general infrastructure backup or always-ready second host is added.

#### Rejected alternative — panel per-client reset at renewal

The per-client `resetTraffic` endpoint, and its bulk/update variants, are rejected for ordinary composite renewal:

- **Not idempotent:** after a lost response, a retry resets again and erases post-renewal usage recorded between the two resets; making it safe would require RX-01 completion/fencing evidence that does not exist.
- **Partial failure:** fan-out per attached inbound, asynchronous for node-hosted inbounds, can leave some of the six fixture children reset and others not, with no returned pre-reset values for reconstruction.
- **Re-enables restricted clients:** `Enable=true`/`Update` conflicts with independent restrictions and pending-renewal rules (FR-041, FR-046, FR-048, FR-053, FR-061) and could reactivate exhausted, expired or suspended access before renewal is effective.
- **Destroys evidence:** zeroed counters conflict with FR-034 (“resets/renewal cannot … erase accrued evidence”) and Constitution II.
- **Does not solve late collection:** pre-boundary bytes collected after the reset land in the new counter, so the boundary question remains.

Also rejected: per-renewal owner usage settlement; deliberate suspension to quiesce counters (FR-046); modifying 3x-UI/Xray or reading core statistics around the panel/provider boundary (NG-04, Constitution V); and exact per-byte boundary splitting, which D1 makes unnecessary.

#### Proposed mechanism

**Observation (D5).** An accepted observation requires HTTP and application success, an object for the verified physical authority + canonical identity with confirmed ownership/topology, and strict nonnegative non-boolean integer upload and download totals. Its observation time is Shopvpn's receipt time; dispatch time is retained for diagnostics. A valid response with unchanged totals is a fresh observation of no new usage. Failed, timed-out, rejected, missing or malformed responses create no observation and never advance time. A response received after a newer accepted one for the same meter is recorded diagnostically and cannot replace it. Freshness (FR-035), grace (FR-036) and current verification use this time; quota/expiry cutoff is still measured from actual crossing (FR-037), so panel collection lag consumes that 60-second budget (E-002).

**Delta chain and epochs (D4).** Per meter and direction, accepted observations form an ordered chain inside a counting epoch. A value at or above its predecessor yields one immutable delta, unique per (meter, direction, epoch, predecessor). A lower value opens the next epoch with that observation as baseline, emits no negative delta, preserves all confirmed deltas and records a decrease gap for the bracketing interval under unchanged FR-034/FR-040/FR-041 handling and drift diagnostics. D4 makes decreases anomalous, not routine. Upload and download epochs remain independent.

**Boundary starting readings (D1/D2).** In the same main-database transaction that makes renewal/conversion effective (RD-02; FR-043/FR-046), after all-child readiness, save for every owned meter and direction its latest accepted observation as the boundary starting reading: meter, direction, epoch, observation ID, value and receipt time. Each current-serving required meter's reading must be at most 60 seconds old at commit (FR-035). The worker re-reads every required meter immediately before committing, so normal age is a few seconds; a missing or stale reading keeps the renewal pending inside its original 15-minute window (FR-046/FR-047). Ingestion and the boundary commit serialize on the main-database writer, so each boundary falls on a chain node: deltas ending at or before it are old-period, deltas starting at it or later are new-period, none spans it, and old plus new deltas equal lifetime deltas exactly once. Boundary readings are immutable; lifetime confirmed usage is never reset.

- Old-period usage `U_old` = confirmed old-period deltas through the boundary readings, across all meters and directions.
- Overrun `O = max(U_old − A_old, 0)`: recorded and absorbed, with no debt (FR-045).
- Carryover `C = max(A_old − U_old, 0)` when eligible under FR-043/FR-044, otherwise 0.
- New available allowance `N = A_new + C`; resulting expiry unchanged from FR-043.
- New-period usage `U_new` = sum of new-period deltas; per meter and direction, (latest value in the boundary epoch − saved value) plus (latest − baseline) for each later epoch, never negative. Display remaining `max(N − U_new, 0)`; exhaustion when `U_new ≥ N` (FR-037).
- Customer effect: if `x` pre-boundary bytes first appear after the boundary readings, reporting-order attribution leaves `max(x − C, 0)` less than exact attribution, which is zero whenever `x ≤ C`. Normally `x` covers about one 3x-UI collection interval plus read→commit latency; under supported normal conditions its ceiling is the 60-second reading-age bound plus one collection interval.

**Retired meters.** Retired identities from leak replacement, movement or emergency cutover are not current-serving required meters (FR-066). If readable at the boundary, they receive fresh readings, and later-reported use, such as native existing sessions (FR-038), counts against the renewed allowance under D1. If a retired meter's latest reading is older than 60 seconds—possible only for an unreachable emergency-exposure meter—its first later delta spans an unknown period and is kept as old-period store-absorbed exposure under FR-066, never renewed-allowance use; subsequent deltas count normally. This limits D1 to normal reporting delay without widening FR-066.

**Restart undercount (D3, bounded by D12).** Because the loss is invisible in totals, record it explicitly as a bounded store-absorbed limitation in the panel capability manifest (up to four collection intervals, 20 seconds at 5 seconds, per restart), and as a non-blocking per-meter annotation when a supported read evidences a restart: on v3.9.0 only Xray restarts are evidenced, through `server/status` `appStats.uptime`; panel-only restarts are not ([GA-MAN-002](#ga-man-002--v-ga-01v-ga-04-lab-run-2026-10-14)). It is never measured zero, staleness, an FR-040 gap or a renewal block. This keeps unobserved consumption explicit under Constitution II without settlement.

**Periodic reset and reset endpoints (D4).** Composite paths never call per-client, bulk or update-traffic endpoints. Child preparation/inspection should verify that no panel periodic traffic reset applies to composite children (field and scope unverified; E-001); a detected configuration is FR-041 drift, and decrease handling remains the safety net.

**Other periods.** Initial/test availability and equivalent-move cutover can use the same chain-node starting-reading rule for new meters; this is a design consequence, not a requirement change.

#### Failure, timing and preservation cases

| Case | Proposed handling and result |
| --- | --- |
| Late-collected traffic | Pre-boundary bytes first reported after the boundary readings count as new-period usage (D1); only `max(x − C, 0)` differs from exact attribution. Bytes reported before the readings are old-period usage or absorbed overrun. |
| Read → boundary window | Bytes used between the pre-commit read and the commit fall after the saved reading and count to the new period. A reading older than 60 seconds at commit requires a re-read; nothing is split by commit or HTTP time. |
| Partial node failure (FR-046/FR-047) | No boundary exists while any required child is pending; old allowance/expiry govern and all deltas stay old-period. Later success saves fresh readings for all meters; failure at the original deadline saves none and changes no counter. Remote partial changes are reconciled under RX-01; accounting needs no rollback because nothing was reset. |
| Retries and lost responses | Boundary inputs are remote reads only: a lost or timed-out read is re-read, and a late older response cannot replace newer evidence. The commit is keyed by the renewal operation; after an indeterminate commit, query that key before retrying (RD-02). Repeated application returns the existing period and immutable readings, so nothing is counted twice. |
| Worker/bot restart | Before commit, the renewal stays pending with its original deadline, then re-reads and commits. After commit, readings, period and deltas are durable, and re-ingesting observations is idempotent. Bot/admin restarts do not affect worker-owned accounting. |
| Decrease near the boundary | Before the readings: an old-period gap under FR-034/FR-040; if carryover is eligible, the renewal stays pending until reconciliation or FR-040 settlement within its window. After the readings: a new-period gap; new-period usage resumes from the new baseline, never negative. |
| Panel/Xray restart; stalled collector | D3 loss, bounded by D12 and including panel-only restarts, is store-absorbed and explicit, not a gap. Failed reads remain stale under FR-035/FR-036. A collector stall with successful responses is undetected D5 residual exposure. |
| Carryover, overrun, restrictions and history | The period stores the readings, `A_old`, `U_old`, `O`, `C`, `A_new`, `N` and expiry. No remote reset or enable is part of the boundary, so independent restrictions, cooldowns, lifetime counters and observation history are unchanged. Reminder periods use `N` and `U_new` (FR-079). |

**RX-01 effect.** The boundary performs no remote mutation, so its retries and restarts need no RX-01 execution proof. RX-01 still governs every remote mutation, including enable/settings convergence to renewed terms, obsolete old-term cutoff reconciliation (FR-085, A15) and revocation. It stays unresolved and continues to block dependent remote-mutation implementation, including the remote readiness steps of renewal application.

#### Proposed detect-and-repair mechanism

1. **Absolute writes.** Every write carries the client's complete desired state (existing contract), so repeating one causes no additional effect.
2. **Direction rule.** A changed, access-reducing desired state (disable, revoke, delete for a restriction) is dispatched immediately; it never waits behind an earlier uncertain request's quarantine. A retry of the *same* desired state waits for the quarantine and a reconciling read-back, as constitution II requires before repeating an uncertain effect. An access-restoring change after an uncertain access-reducing request waits for that request's quarantine, avoiding off/on flapping; this wait is a configurable setting. Such waits count against the original clocks (for example FR-054's 60 seconds or the 15-minute renewal window), which never restart.
3. **Uncertain requests and quarantine.** A request that times out, or whose outcome is unknown after a crash following dispatch, becomes `uncertain`. Its quarantine runs for Q from when Shopvpn abandoned it and closed its connection. At quarantine end, read the client back and write the desired state if it differs.
4. **Meaning of "confirmed".** A client's desired state is confirmed when all three hold:
   - no uncertain request for that client is still in quarantine;
   - a read-back after the latest write matches the desired state;
   - where a requirement needs it, runtime fresh-authentication evidence exists (`confirm_runtime_state`, still an E-001 capability).

   Confirmation drives customer/owner status (FR-007), leak-replacement delivery and cooldown start (FR-055/FR-056), final-cancellation completion (FR-060) and renewal readiness (FR-046). A later divergence found by the sweep is recorded against the confirmed state, repaired and shown; it never silently rewrites confirmation history.
5. **Continuous sweep.** For every panel serving composites, read each composite inbound's client list every S seconds; one read covers every client on that inbound.
   - Compare every owned identity, including fulfilled, inactive and cleanup-pending ones, with its desired state, and flag reappearance of deleted identities.
   - Repair mismatches by writing the desired state, and record each divergence.
   - The sweep never stops. It is what bounds RX-D1's residual, and it implements FR-041 drift detection.
   - Sweep reads have a finite timeout. A failed or timed-out sweep is `unknown`, never `consistent`.
   - At a lower cadence the sweep also re-verifies RX-D2's setting. A panel reporting it on, or whose setting cannot be read, is blocked from new composite binding and raised as FR-041 drift.
6. **Repeated divergence.** If one client diverges more than N times within window W, something other than a stale request is changing it. Open an FR-041 discrepancy for owner investigation. While it is open, access-reducing repairs continue (fail-safe) and access-restoring repairs pause.
7. **Repair failures and panel stalls.**
   - A repair write that times out becomes an uncertain request under item 3; after R failed repairs, escalate.
   - If writes on a panel or inbound repeatedly fail to complete within threshold T, raise a panel-stall escalation: owner web-admin attention, an attempted Telegram alert and pending customer status.
   - During a stall, protective intents are still accepted, refunds are not delayed and other panels continue.
   - Automatic panel-only restart awaits RX-D3.
8. **Scope.** The quarantine applies per client, provided V-RX-01(c) shows no lost updates between clients of one inbound; otherwise it widens to the inbound. Shopvpn's own writes to one physical panel stay serialized by the per-panel lock, including aliases and affected legacy writers (RD-03).
9. **Terminal revocation.** This covers leak-replaced old credentials, permanently cancelled subscriptions, retired servers after a move or emergency cutover, and failed initial-fulfillment cleanup.
   - Disable immediately and record final traffic.
   - Delete only after the client's quarantine has ended and its meter has stopped growing for settle period P, because open native sessions keep emitting traffic under RX-D2. Batch deletes per panel.
   - A stale update that starts after the delete fails at the client lookup (source fact 3). Traffic after deletion is unmetered and recorded as exposure on the cleanup obligation.
10. **Values.** The owner sets Q, S (30 seconds proposed), the restore-wait setting, N/W, R, T and P from V-RX-01 measurements, and records them like D12.

**Rejected alternatives:**
- Strict fencing: no v3.9.0 mechanism exists, and modifying 3x-UI/Xray is out of scope (NG-04).
- A time-limited watch, for example 10 minutes: it misses requests delayed beyond the watch, and no natural bound exists (inference i).
- Holding access-reducing writes behind a quarantine: it would delay quota cutoff, leak revocation and cancellation.
- Keeping `restartXrayOnClientDisable` on: see RX-D2.

The source-based failure scenario in RD-03 remains valid; RX-D1 accepts its residual instead of preventing it.
