# Migration, maintenance, deployment and recovery contracts

These are proposed changes to affected `database.py`, `backup.py`, `fsm_storage.py`, `main.py`, `bot_manager.py`, bot/web restore callers and `install.sh`/`manage.sh`/`update.sh`, plus `composite/operations.py`/`cli.py`. No source/deployment change or operation is executed by this plan. E-004/E-005 remain required evidence.

## Shared processing control

All affected processes use an external protected installation/restore-epoch control record and POSIX admission lock outside replaceable database/FSM files. Shared permission covers normal dependent transactions/remote dispatch; maintenance exclusive permission prevents new writers/effects. Worker/panel singleton and per-panel mutation locks are distinct from maintenance. Every participant registers incarnation, open DB/FSM handles and in-flight remote scope; old incarnation may not acknowledge a new epoch. No reliance on a per-Database thread lock as global closure.

Proposed `enter_maintenance(reason, expected_epoch) -> MaintenanceReceipt` closes admission, drains bounded active operations, stops bot reconciler/purge/cache/task reopening, API notifier/background writers and public readers for file replacement, then verifies affected processes/handles closed. Failure to stop a writer is a blocking failure, not a warning followed by overwrite. Persist any dispatched indeterminate remote effect; a closed local process is not proof remote request was cancelled. Preserve all original commercial clocks. Backup freezes local writers briefly without restarting panel/Xray or terminating customer sessions; recovery replacement is a separate outage. Measure pause/detection/urgent-work delay before accepting scheduling.

Proposed `leave_maintenance(receipt, validated_state, next_epoch)`: reopen only version-compatible participants; worker starts in reconciliation/hold mode, obsolete leases/purge requests are fenced, independently verified records resume. For snapshot-only capture with no replacement, preserve epoch and remote-state semantics. Unexpected coordinator death leaves maintenance/recovery marker explicit; no process silently restores mutation permission from stale memory.

## Additive upgrade

Proposed `inspect_schema` and `migrate(authorized_paths, expected_release)` are versioned, repeat-safe and testable against supported prior schemas. Existing `init_db`/`_migrate_columns` are foundations, not proof. Ship guard/discriminator support before permitting issuance; default existing rows to legacy, preserve users.telegram_id/FSM/defaults/provider meanings and manual/automatic renewal distinction. Main holds composite tables; affected reseller files get only required compatibility/operation metadata, no composite eligibility or automatic data import. Enumerate active/inactive/no-live-bot registry tenants, validate unique paths/identity and owner preservation.

Before migration: identify exact release/runtime/dependency versions, schema ranges/config/key changes; coordinate all writers and capture complete pre-upgrade recovery set. Each DB's migration owns explicit transaction boundaries and does not nest committing helper calls or use a script's implicit commit as atomicity. Multi-file failures retain per-member outcome, leave issuance disabled and restore or repair coherently; no main-only apparent success. Run FK/integrity/schema/index/data/effect/capacity invariants and rerun initialization before reopening. Older binaries must be fenced from active new semantics. No schema drop or invalid old-code rollback over live children.

## Recovery archive

Proposed `capture_recovery_set -> RecoveryPoint` contains main DB (wallet/order/customer/coupon/test/campaign, entitlement/tokens/meter/period/gaps/current+retired identities/work/audit), all explicitly required dependent reseller DBs, affected FSM, release/schema/runtime inventory and machine-readable manifest. Manifest includes installation/capture epoch/time, every expected member and ownership/path identity, checksums, validation results and exclusions. Accept existing `reseller_<id>.db` and historical `reseller_<id>_level<N>.db` mapping, never infer a safe path from archive name alone.

Use SQLite online backup per file under the coherent writer barrier; checkpoint only with appropriate closure, never copy a changing DB while ignoring WAL. Validate integrity/FKs/schema compatibility/domain invariants and missing/corrupt/unexpected/path-traversal/duplicate members in staging. Legacy pre-feature archives without complete manifests need explicit reconstruction/validation and cannot establish no later composite history. They are supported recovery inputs with holds, not automatic safe replacements.

Encrypt archive using versioned authenticated encryption (existing cryptography), store/deliver to owner-authorized off-host SFTP with pinned verified host identity, restricted credentials/access and independently retained keys. No `known_hosts=None`. Completed off-host checksum/validation and capture time establish freshness; transfer attempt/file mtime do not. Candidate cadence5minutes must maintain last verified recoverable capture≤15minutes normally including capture/validation/delivery; measure it. Unknown/overdue copy prompts owner web attention and attempted Telegram alert, without automatic mass suspension/refund.

Exclusions: unencrypted environment/decryption/private keys, remote panel/Xray infrastructure, external HTTPS/domain/routing control and machine-wide state. Authoritative DBs may contain authorized tenant secrets and require protected handling. External release/config/key/domain/TLS/prepared-panel recovery inventory is separately maintained; FSM included where needed for observable conversation recovery. Raw samples may compact only with preserved confirmed totals/epochs/allocations/gaps/effect history/tombstones and cleanup responsibility. No hardcoded evidence-erasure horizon or general infrastructure backup service.

## Restore and stale-history reconciliation

Proposed `preflight_restore(archive, external_inventory) -> RestorePreview` decrypts in authorized isolation, validates entire set/member manifests/schema/data/path safety before replacing any main/tenant file, compares current installation/registry/dependencies and reports gaps/skew/missing members. Preserve current complete pre-restore set and newer accessible journals/evidence externally before destructive replacement; include all pre-copy paths in results. Refuse silent partial replacement; if physical replacement is interrupted, remain in maintenance with recovery copy and explicit per-member recovery state.

`restore_validated_set(preview, owner_authorization) -> RecoveryCase` verifies writer stop/closed handles, increments external restore epoch, replaces staged validated set coherently with recoverable checkpoints and cache invalidation, migrates as needed, then starts safe reconciliation before dependent mutations. No stale reconciler/purge can restart writers during replacement. Missing newer files are neither silently retained as a mixed set nor blindly deleted; preview/holds record treatment. Old snapshot/schema alone does not prove current remote identities, money, allowance or campaign capacity.

Reconciliation evaluates preserved newer local evidence and independently verifiable payment references, panel-owned identities/runtime state, token/generation/revocation facts, usage/reset/boundary evidence and coupon/test/campaign outcomes. Hold uncertain effects; never blindly refund/debit/create/enable/reset/reopen claims from snapshot. Pursue safe suspension/cleanup only for verified owned identities, retaining pending native exposure. Snapshot absence is not proof of remote cleanup or no past receipt. There is no zero-history-loss reconstruction promise. Release verified cases independently; widen hold only if affected shared state cannot safely isolate. Usage-only settlement requires intact ownership/purchase/lifecycle/financial/campaign history; other irrecoverable gaps require specific governed remediation/risk acceptance with maintainer/reason/evidence/scope/follow-up, never preapproved generic owner resume.

Report original deadlines/overdue refunds/cleanup/unknown claims/missed targets as soon as safe processing resumes. With beneficiary/amount/prior outcome established, overdue credit becomes spendable within60seconds; otherwise visible evidence hold precedes any repetition. Retain original expiry/grace/cooldown/campaign history and known newer cancellations/rotations. A recovery hold is not confirmed remote cutoff.

Prepared-host recovery target is four elapsed hours from owner initiation **with** prepared host, validated required copy, selected release/runtime/config/authorized keys and functioning external HTTPS/domain/panel prerequisites. Report waiting/procurement/owner response separately; retries never restart clock. Completion evidence includes main Telegram customer and owner web management, existing public URL identities, safe accounting/enforcement/recovery for verified records and truthful held/partial functions. Running processes/copied files are insufficient. No always-ready second host or automatic extension/refund.

## Destructive guard and rollback

Guard in the shared service/database boundary for factory reset, customer/order/subscription/panel/plan removal, tenant tier/delete/ownership/purge and invalidated/stale cleanup requests. Check protected ownership/money/period/usage/token/campaign/remote obligations and all sole dependent management/key references. Return sanitized blocking record/obligation IDs and allowed cancellation/cleanup/equivalent-move guidance. `force`/confirmation cannot bypass. Keeping composite tables while deleting their dependencies is forbidden. Cancelling/refunding every subscription still does not authorize history erasure. Ordinary test reset remains, preserving unresolved holds/permanent campaign recipients. Deactivation excludes new offers/claims, retains existing management/cleanup; it does not automatically revoke access.

Rollback before new issuance may restore tested pre-upgrade state after coherent writer coordination and no new effects. After feature effects, use compatible feature-aware release or validated restoration+newer-evidence reconciliation; old binaries cannot ignore composite work/tokens/refunds and be considered safe. Retain pre-rollback history/cleanup and external keys. Rollback is not a way to reset deadlines/counters/grants/claims.
