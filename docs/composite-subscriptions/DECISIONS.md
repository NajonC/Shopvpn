**Contracts to finalize in P0**

The coordinator should attach reviewed, language-level signatures and data shapes to the decisions above. Do not assign implementation packages with only guessed function names.

- **Repository contract:** create/resume by fulfillment identity, enumerate owned children/meters with mirror-aware addressing, accept samples transactionally, change desired state/revision, claim/acknowledge operations, preserve tombstones through tenant cleanup/transfer, and query tenant-owned services.
- **Panel contract:** target a specific server/inbound/credential; distinguish missing, transient failure and invalid response; ensure creation without unsafe adoption; return validated counters and identity/scope; apply absolute desired fields; confirm disable/delete; export complete node settings.
- **Accounting contract:** counter scope and epochs, idempotent delta application, billing period rules, sample freshness, and the relationship between measured usage and desired revocation.
- **Lifecycle contract:** state transitions for provisioning, partial availability, enabled/disabled, exhaustion/expiry, renewal, rotation, deletion, reseller tier changes and ownership transfer. Separate desired state from confirmed remote state, including work surviving a database restore.
- **Payload contract:** normalized node inputs, stable ordering, format negotiation, complete transport/security fields, aggregate metadata for apps/alerts, revoked-state behavior, and cache eligibility during outages or recovery.
- **Recovery contract:** backup contents and scope, schema compatibility, cross-process maintenance, restore generation/operation handling, meter settlement, missing-identity discovery and explicit uncertainty before normal processing resumes. No guarantee of exact history reconstruction from a stale snapshot alone.

**An important limitation to retain**

If B's API becomes unreachable while its data path stays active, the coordinator cannot immediately know or stop all B traffic. Keeping B's last confirmed total avoids a false zero but only provides a lower bound. An outage policy must state what is guaranteed, what remains unknown, and what local mechanisms enforce expiry or quota. A completed API call also does not by itself prove an established connection has stopped; verify that in staging.

**Decision record template**

For each resolved decision, add: ID; proposed choice; alternatives rejected and why; source/deployed-version evidence; user confirmation where business behavior changes; exact contracts affected; linked acceptance cases; and date/revision. Keep `proposed`, `approved`, `implemented`, and `verified` distinct. Do not label a decision approved solely because another agent recommended it.
