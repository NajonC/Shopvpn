## Requirement and policy boundaries

**Accepted feature requirements:** one purchased subscription owns arbitrary child credentials, exercised by the six-node topology below; A uses a single REALITY inbound on port 443, with no additional listener or Layer-4 proxy; one public subscription URL exposes all six nodes with meaningful remarks; all child traffic consumes one purchased bucket; exhaustion or expiry triggers revocation of every child across all three servers. SQLite remains in scope and database replacement is deferred. Six nodes is a fixture, not a hardcoded limit.

**Recommended engineering acceptance conditions:** durable operation recovery, idempotent fulfillment, preserved traffic history, ownership isolation, and legacy-service compatibility. The scenarios below propose concrete checks for these conditions. They are implementation recommendations supporting the accepted feature, not additional product decisions already approved by the user.

**Open choices to resolve before the applicable gate:**

- Quota unit and display convention: decimal GB versus the current code's binary GiB; exact byte conversion and rounding.
- Poll cadence, maximum tolerated sample age, retry/backoff policy, enforcement delay and overshoot budget, and behavior while a panel API is unavailable but its VPN remains usable. No interval or exact zero-overshoot guarantee is set here.
- Subscription start time, absolute expiry semantics, renewal policy, and the precedence of paid renewal, manual suspension, exhaustion, and deletion. Preserve explicit operator decisions when defining this ordering.
- Behavior when a remote traffic counter resets without a reliable epoch marker, including whether uncertain usage requires intervention or restricted access.
- Rollback versus recover-forward after partial provisioning, and whether any partial activation is allowed. The recommendation is to deliver a ready subscription only when all six children are confirmed usable.
- Base64/raw URI, Clash, and sing-box delivery support, selection rules, and client/version matrix. The original request includes these formats for assessment; this specification neither commits all formats to the first release nor silently reduces the scope to Base64.
- Cached configuration behavior during panel outages, retention/deletion of credential material and tombstones, public token rotation, and termination expectations for already-established proxy flows.
- Composite renewal policy despite the upstream manual-carryover/automatic-replacement distinction; whether tenant tier changes or deletion revoke services or transfer their management responsibility.
- Backup compatibility, acceptable data-loss window, incomplete cross-database snapshots, restore maintenance coordination, and treatment of history missing from both the snapshot and live panels. Exact recovery cannot be assumed after unobserved resets or lost lifecycle events.

## Reference fixture

Create subscriber Ali with a single purchased subscription, a 50 GB displayed quota resolved to an explicit integer byte limit `Q`, and a 30-day term resolved to an absolute expiry `E`. Use fresh staging resources with no production customers.

| Node key | Panel | Remote inbound | Independent authenticated identity | Expected egress/remark |
|---|---|---|---|---|
| `a_us` | A | A's single REALITY inbound, port 443 | `ali_sub1_us`, UUID A1 | US route; `🇺🇸 US - Reality` |
| `a_de` | A | The same inbound as `a_us` | `ali_sub1_de`, UUID A2 | DE route; `🇩🇪 DE - Reality` |
| `a_ru` | A | The same inbound as `a_us` | `ali_sub1_ru`, UUID A3 | RU route; `🇷🇺 RU - Reality` |
| `b_cdn` | B | B inbound 1, VLESS-WS-CDN | Independent B1 credential | `Server B - CDN` |
| `b_grpc` | B | B inbound 2, Trojan-gRPC | Independent B2 credential | `Server B - gRPC` |
| `c_direct` | C | C inbound 1, VMess-TCP-TLS | Independent C1 credential | `Server C - Direct` |

Client emails shown above describe identities, not a mandated production naming convention. B/C inbound IDs may collide numerically with A's IDs: addressing must include the panel. A second subscription for Ali and a subscription for another customer must exist in isolation tests. If deployments support separate bot databases or reseller scopes, add a second scope containing overlapping local numeric IDs and usernames.

For the refresh scenarios, add main-registry and tenant-local mirror rows for one physical panel, volume-credit and fixed-product inventory fixtures, a tenant without a live bot, and snapshots from both source baselines plus the eventual feature schema. Include pending operations and a retired credential generation in recovery fixtures. Exercise only approved composite tenant modes; keep the remaining fixtures for legacy compatibility checks.

## Automated gates with isolated SQLite and mocked panels

Tests in this section must use temporary databases and deterministic panel responses; they must not contact customer panels or send real Telegram messages. Simulate interleavings and failures at durable state boundaries instead of relying on sleep-based timing.

| ID | Scenario | Acceptance evidence |
|---|---|---|
| A01 | Migrate an existing SQLite database and initialize a new database; repeat initialization. | Existing records and ownership remain intact. New tables/indices exist once. Migration preserves the distinction between `users.id` and Telegram IDs. A failed migration is detected and leaves a recoverable database. |
| A02 | Persist and provision the complete reference fixture, including staggered child creation. | One parent owns exactly six independent child identities. Three children may reference A's same inbound. B's children target only their intended inbounds. Server-qualified inbound identity prevents collisions; an invalid parent or server reference is rejected. Remote fields include the required protocol/authentication settings (including flow where required) and the same chosen absolute expiry; payload serialization cannot compensate for wrong remote creation. |
| A03 | Repeat the same paid-order fulfillment, including simultaneous callbacks. | One entitlement per intended purchased unit and one stable identity per child are recorded. Retrying notification or fulfillment does not create another subscription, charge again, or allocate fresh credentials. Multiple purchased units follow an explicitly defined order-to-subscription mapping. |
| A04 | Panel accepts a client create, then the request times out before the bot records success. | Retry searches for the persisted intended identity and confirms its server/inbound/credential ownership. It neither creates a duplicate nor adopts a different pre-existing identity with a matching email. Ambiguity remains visible and retryable. |
| A05 | Fail after any child creation or activation, including failure on B after A succeeds. | Every attempted remote identity remains durably addressable. Recovery follows the chosen rollback/recover-forward policy. Fulfillment status and delivered link do not claim six usable nodes prematurely. |
| A06 | Restart the worker before a request, after remote success, before local acknowledgement, and during a retry. | Pending operations survive; obsolete leases can be recovered; reconciliation reaches the current desired state without duplicate effects. A crash does not erase credentials needed to finish revocation. |
| A07 | Poll all six independent meters with known upload/download values; fetch the same samples twice. | Total consumption equals `A_US + A_DE + A_RU + B_1 + B_2 + C_1`, counting upload and download exactly once. Repeated samples do not increment the ledger again. Parent quota remains `Q`, not six separate grants presented as one. |
| A08 | Import a legacy remote identity attached to two inbounds, whose API exposes a single shared traffic record. | Attachment count does not multiply its traffic. Ownership maps both attachments to one canonical meter. Truly independent identities still use distinct meters; the same remote meter cannot silently belong to unrelated subscriptions. |
| A09 | Timeout B or C; return HTTP 200 with `success:false`, missing/malformed traffic objects, negative counters, booleans, or nonintegral values. | Invalid readings are not accepted as zero. Last confirmed cumulative usage remains intact and is marked stale. Healthy subscriptions and healthy panels continue processing. Unavailability does not restart the worker or reset the bucket. |
| A10 | Deliver out-of-order samples and overlapping poll completions. | Older samples cannot overwrite newer baselines or inflate cumulative bytes. A reading started under an old credential/counter epoch cannot be assigned to its replacement. Record the sampling/version mechanism used to enforce this. |
| A11 | Reset upload and download counters independently, reset both, replace a credential, and observe an unexplained counter drop. | Confirmed old-epoch usage is retained. New-epoch deltas are credited once with separate upload/download baselines where needed. Unknown resets enter the chosen uncertainty policy; they do not fabricate an exact total or grant a new bucket automatically. |
| A12 | Reach `Q-1`, exactly `Q`, and greater than `Q`; cross `E` with no successful traffic response. | The byte threshold uses integer arithmetic. At `Q` or above, every child receives the exhausted desired state. Expiry enforcement does not depend on fresh traffic. Tests include clock/unit conversion and the chosen quota convention. |
| A13 | Only a partial current sum is available but the retained confirmed total already reaches `Q`. | The subscription enters revocation even when another panel is stale. Healthy children are revoked promptly under the chosen policy; unreachable children remain pending rather than falsely confirmed disabled. |
| A14 | Apply disable, renewal, quota adjustment, and credential rotation through a replacement-style panel update API. | A fresh canonical payload preserves unrelated identity, flow, transport-related client fields and limits. Mutation scope follows the verified API version. For an email-wide API, one canonical update per intended identity avoids redundant attachment updates; inbound-scoped APIs must cover every intended attachment. Resets/renames do not repeat effects solely because an identity has multiple attachments. Disable never implicitly enables or resets counters. |
| A15 | Interleave renewal with exhaustion, expiry, manual suspension, queued enable, and queued disable; complete requests out of order. | One explicit subscription revision/state ordering determines the result. Stale work cannot permanently re-enable a revoked subscription or disable an accepted newer renewal. If a stale remote request completes, reconciliation corrects it and reports any temporary divergence. Payment handling and entitlement application remain idempotent. |
| A16 | Revoke the parent while B is offline; restart and later restore B. Also stop the entire accounting coordinator while VPN data paths remain available. | A/C receive the desired state; B's operation remains durable and is retried. The parent exposes pending convergence. Completion means every required child has confirmed the intended remote state. Retry exhaustion must not silently discard work. Coordinator-outage exposure follows D02; worker recovery catches up before treating old usage as current, and no unavailable coordinator is claimed to guarantee timely global cutoff. |
| A17 | Delete a subscription while one panel times out or reports application-level failure; retry a confirmed-absent client. | Tombstones retain server/inbound/identity references and cleanup state until absence is confirmed according to the retention policy. Idempotent absence is successful. HTTP status alone cannot mark a rejected deletion successful. A local delete cannot orphan unmanaged remote access. |
| A18 | Run two workers against the same SQLite data while both update related and unrelated subscriptions. | Claims prevent duplicate work; subscription revisions serialize conflicting intent; panel mutation coordination avoids conflicting writes. Transactions remain short and bounded; lock contention is retried or surfaced without lost accounting. The test topology matches the supported process deployment. |
| A19 | Customer, bot/reseller scope, order, child, meter, and token ownership boundaries. | Unauthorized callers cannot read payloads, usage, credentials or lifecycle controls for another owner. Colliding IDs across scopes do not redirect operations. Public subscription access is scoped to the token's parent; secret tokens and panel credentials are not exposed in routine logs/errors. |
| A20 | A valid/unknown/revoked public token and repeated concurrent subscription downloads. | A valid ready subscription produces the intended six-node set from its own children. Unknown/revoked-token behavior follows the selected policy without exposing another parent. Downloading a payload does not create clients, reset usage, or trigger a renewal. |
| A21 | Render every agreed payload format from six representative native configurations, including Unicode remarks. | One node per intended fixture endpoint, stable ordering, distinct remarks/tags, valid whole-payload encoding, and preserved UUID/password, address, port, REALITY key/short ID/server name, VLESS flow, TLS and transport fields. | A24 | Change a plan's topology after purchase; explicitly remove a node, replace a panel, or change a child's route. | Existing purchases retain their agreed snapshot unless an explicit migration is initiated. | A27 | Provision in each approved tenant mode, including `has_live_bot=0`; stop Telegram polling or hide the optional web/Mini App UI. | Every active composite entitlement still receives accounting, expiry and revocation processing from its designated worker. Partial ownership transfer across databases is recoverable; customer and supplier/inventory ownership follow the explicitly chosen transfer policy, and unrelated tenants remain isolated. Repeated cleanup does not recreate or re-enable credentials. |
| A30 | Back up and restore historical, refreshed pre-feature, and feature schemas; test both reseller ZIP naming formats, incomplete archives, incompatible versions, multi-DB snapshot skew, entirely absent expected tenant archive members, and failure after main replacement but before tenant completion. | Database snapshots contain all stored parent/token/child/meter/billing/operation records. Old schemas migrate before consumers resume and retain legacy data without inventing later purchases. Unsupported schema downgrades and missing/corrupt required tenant copies are detected against the expected registry, not only files present in the archive. Partial replacement or retained newer tenant files cannot be reported as a coherent completed restore. Cross-database credit/entitlement inconsistency is reconciled or explicitly pending; tokens retain their intended identity and external URL prerequisites are documented. |
| A31 | Restore a snapshot showing 20 GB used when same-epoch live counters show 50 GB exhausted; repeat after counter reset, renewal, revocation, rotation and creation of children absent from the snapshot, stale file-purge jobs, and bot reconciliation restarting a stopped tenant during restore. | Recoverable same-epoch usage catches up before allowance is granted. Unknown history follows D08/D13 instead of promising an exact total or blindly re-enabling/recreating clients. All writers and in-flight mutations participate in the recovery protocol; work from before the restore cannot permanently override recovered desired state or erase needed recovery records through stale destructive operations. Discoverable orphan identities require verified ownership before adoption/cleanup. Missing panels and unrecoverable records stay visible until resolved. |
| A32 | Feed aggregate subscription metadata to the new connection-alert worker and Mini App connection-status display, including partial/negative metadata, non-success HTTP responses carrying headers, stale/failed/cached readings, renewal/rotation, distinct alert thresholds and failed notification delivery. | Usage/expiry metadata describes the parent, not six independent purchased quotas. The accounting assertions must be stated using a canonical meter, not a count of rows:

```text
same confirmed meter epoch:
    delta_upload   = sampled_upload   - previous_upload
    delta_download = sampled_download - previous_download
    cumulative_meter_bytes += delta_upload + delta_download

invalid, stale, or failed read:
    retain cumulative_meter_bytes and expose freshness/uncertainty

parent consumed bytes =
    sum(cumulative bytes of distinct owned meters)
    - any explicitly defined billing-period baseline
```

Negative deltas require the epoch/reset policy in A11; they are not ordinary consumption. A billing-period baseline is used only if the selected renewal policy calls for a fresh period. A stale total is a lower bound on actual usage, not evidence of zero additional consumption.

Mocks cannot establish native Xray behavior, actual panel compatibility, egress correctness, or performance. Execute these gates against the exact intended versions and configuration, after automated acceptance passes and open policies affecting each gate are recorded.

## Release evidence

For each ID, retain the implementation revision, fixture, expected result, observed result, and a pass/fail/not-run status. For staging, also record panel/core/client versions and the selected policy values. Redact credentials, API tokens and public subscription tokens from evidence.

Do not mark the feature ready because unit tests pass alone. The applicable deployed-panel and client gates must pass, unresolved scope/policy decisions must be explicit, and failures must have either a fix with a rerun or a documented user-approved change to the requirement. A not-run scenario remains unverified.
